## Problem

Each swarm runs on one tokio task. Its loop, `ConsensusNetwork::run` (`crates/network-libp2p/src/consensus.rs:772-790`), selects over a record-refresh tick, the swarm stream and a 100-item command channel (`consensus.rs:587`) carrying `SendRequest`, `SendResponse` and `Publish` (`crates/network-libp2p/src/types.rs:350`, `:383`, `:408`).

Accepting an inbound connection is synchronous work on that task, and no source address is validated first — validation means a completed round trip through the address (RFC 9000 section 8.1). `libp2p-quic` accepts every attempt unconditionally (`libp2p-quic-0.14.0/src/transport.rs:595`). One accept's cost is {{quic-initial-unvalidated-cost}}; the endpoint-state lock it holds throughout, taken by the endpoint driver too, quinn's background task for an endpoint (`quinn-0.11.9/src/endpoint.rs:419`, `:367`), is {{endpoint-driver-contention}}. One poll carries one accept (`transport.rs:615`; `libp2p-swarm-0.48.0/src/lib.rs:994-999`), and behaviours, polled ahead of the listeners, are not starved (`lib.rs:1189-1198`).

What is unbounded is how long the task runs before yielding. `process_event` (`consensus.rs:800-857`) has no `.await`, an inbound-connection event falls to its catch-all arm (`consensus.rs:854`), and the future the listener waits on polls a `tokio::sync::Notify` (`quinn-0.11.9/src/endpoint.rs:641-669`) that spends no cooperative budget. That budget — 128 units (`tokio-1.53.1/src/task/coop/mod.rs:115-116`), installed once per task poll (`tokio-1.53.1/src/runtime/scheduler/multi_thread/worker.rs:689`) — is the allowance one poll gets, and four parts of this loop draw it down: the command channel (`tokio-1.53.1/src/sync/mpsc/chan.rs:295`), the record-refresh tick (`tokio-1.53.1/src/time/sleep.rs:404-410`) and two behaviour-internal `tokio::time::Interval`s, the peer-manager heartbeat (`peers/behavior.rs:185`) and the stream sweep, the tick that expires stale stream opens and drops expired rate-limit windows (`stream/behavior.rs:361`). A poll that comes back `Pending` returns the unit it drew (`coop/mod.rs:279-289`), so the budget runs out after about 128 delivered commands or ticks rather than after 128 turns of the loop, and once it is out those four stay `Pending` until the task yields and its next poll installs a fresh budget. Two of the four, the behaviour timers, are polled through the swarm branch, so that branch does draw budget whenever one of them ticks. The accept path inside the same branch draws none, because the `Notify` it waits on never enters the budget, and steady arrivals therefore keep that branch ready and producing events at no charge.

So the stall has an onset. Until those 128 units are spent the `select!` still serves the command channel and the ticks, each branch taking its turn from the macro's random start (`tokio-1.53.1/src/macros/select.rs:808`); once a stretch of work with no yield in it has spent them, and for as long as attempts keep arriving faster than the task retires them, the node goes on accepting connections and stops doing what it was asked: nothing published, no request or response sent, no record refresh or peer maintenance, no reply to a command it waits on. `wait_for_network_peers`, which an epoch start runs, waits on one such command: `established_peer_count` sends over that channel and awaits a oneshot (`types.rs:704-708`), and the caller's `.unwrap_or(0)` turns only a closed channel into zero, not a pending one (`crates/node/src/manager/node/start_epoch.rs:964-978`). If an epoch start's wait falls inside such a stretch, with the budget spent and attempts still arriving, the send blocks once the channel fills, the reply has no timeout, and the retry counter never advances, so the wait hangs without bound, neither timing out nor reaching its 240-try, 120-second fatal exit. None of this has been observed; it is read off the code above.

## Goal

- **A bound on the age of the oldest command waiting on the swarm task, and on how long the task runs between yields**, neither growing as attempts arrive faster. *Observable:* histograms of both, beside the achieved tick intervals of the refresh, heartbeat and sweep. *Baseline:* neither is exported today, the node's only inbound counter being one for established connections (`crates/network-libp2p/src/metrics.rs:154`); the maintainers set both bounds from **Task yields and command age under sustained arrivals**.
- **Honest peers unaffected.** With all ten committee members of the reference deployment (see Background) reconnecting at once, no honest handshake is refused and first-dial-to-established time, gossip delay and round-trip time stay within what **An honest full-committee reconnect** records, to a tolerance set from it.
- **Non-goals.** What one accept costs ({{quic-initial-unvalidated-cost}}). Endpoint-state contention ({{endpoint-driver-contention}}). An attempt's fate once accepted ({{pending-inbound-unbounded}}). Surviving a link-saturating flood.
- The issue closes when those counters exist and the two runs below, **Task yields and command age under sustained arrivals** and **An honest full-committee reconnect**, are recorded against them, with the per-attempt time **Time on the swarm task per accepted attempt** asks for read during the first.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

An Initial — the first packet of a connection attempt, carrying the TLS ClientHello and at least 1,200 bytes (RFC 9000 section 14.1) — that the task has not reached waits in quinn's incoming buffer: 65,536 attempts and 100 MiB at the `quinn-proto` defaults (`quinn-proto-0.11.18/src/config/mod.rs:251-253`), first in, first out; while it is saturated an arriving Initial is ignored before Initial keys are derived, as it has been since `quinn-proto` 0.11.15 (`endpoint.rs:455-461`, keys at `:463`; `quinn-rs/quinn#2683`). `libp2p-quic` leaves both defaults alone, setting only the transport parameters and `migration(false)` on the server configuration (`libp2p-quic-0.14.0/src/config.rs:157-162`), so the reference deployment's two swarms hold at most 131,072 waiting attempts and 200 MiB between them, against the host's 32 GB: derived from those defaults, not measured.

### Approaches surveyed so far

Bound how many attempts the transport handles before it yields. The poll function performing the accept is private and `libp2p_quic::Config` exposes only timeouts and stream windows (`libp2p-quic-0.14.0/src/transport.rs:419`, `config.rs:30-60`); a count kept there counts accepts rather than time on the task, and the transport crate sees nothing of the command channel or the ticks such a bound is for (`crates/network-libp2p/src/consensus.rs:772-790`).

Move the accept off the swarm task. It runs holding the endpoint-state lock the Problem names, so the work changes task while the serialization may not, and listener ownership sits in `libp2p-quic` (`transport.rs:419`) rather than in this repository.

Order this repository's own `select!` so the command channel and the refresh tick precede the swarm. Without `biased;` the macro starts at a random branch (`select.rs:808`), so an order settles which of this loop's three branches is offered first; the order in which one swarm poll reaches its own behaviours, connections and listeners is libp2p's (`libp2p-swarm-0.48.0/src/lib.rs:1189-1198`), and the budget a branch draws from is installed per task poll (`worker.rs:689`) rather than per branch, so being offered first and having a unit left to draw are different things.

Yield from this repository's own `run` loop, which receives an event per accepted attempt (`libp2p-swarm-0.48.0/src/lib.rs:994-999`). The accept has run by then (`transport.rs:595`), so this changes when the next starts, not what one costs or where the backlog waits; the runtime's two yields, an unconditional one and a budget-driven one (`tokio-1.53.1/src/task/yield_now.rs:38`, `coop/consume_budget.rs:25`), carry no criterion for how often this loop should take one, and this issue does not settle it; and gossip and request-response events share the loop, so whatever criterion is chosen they pay for it too.

A change inside the poll function or the listener that `libp2p-quic` keeps to itself (`libp2p-quic-0.14.0/src/transport.rs:419`) would be carried as a modified transport crate, and that upkeep is {{patched-transport-crate-upkeep}}; that is where bounding the transport's accepts and moving the accept off the swarm task would sit.

## Implementation details to pay close attention to

If accepts are deferred, whether because attempts are held back or because the task yields before taking the next one, the remainder waits in a queue that cannot tell an honest reconnect from a flood, and discards at accept anything older than the 30 s idle timeout (`quinn-proto-0.11.18/src/endpoint.rs:569-581`; `crates/config/src/network.rs:401`); a deferral tight against a committee-wide reconnect or epoch change turns it into queueing against that deadline.

If a yield is taken per event, gossip and request-response events pay the same round trip as inbound attempts, so ordinary latency follows a criterion chosen for the flood.

If a scheduling decision is keyed on a source address that has not completed a round trip, that key is attacker-controlled, a precondition owned by {{quic-initial-unvalidated-cost}}.

If an attempt waits longer than it does today before being accepted, nothing on the wire tells its sender: the stale-attempt drop above sends no packet at all (`response: None`, `quinn-proto-0.11.18/src/endpoint.rs:569-581`), and an accepted attempt whose upgrade outruns the swarm builder's 10 s default is dropped after it (`libp2p-0.57.0/src/builder/phase/swarm.rs:5`, applied at `build.rs:28`; this node sets no other value, `crates/network-libp2p/src/consensus.rs:563-582`). A peer on stock crates of this release or the previous one has only its own dial deadline to go on, and what it does at that deadline — retry, back off, or give the address up — is not established here ({{quic-listener-interop-tests}}).

Setting the two bounds the first Goal item asks for takes inputs this issue does not fix: the reference deployment's committee of ten and its two swarms per host (see Background), the eight established connections per peer the node already allows (`crates/network-libp2p/src/consensus.rs:124`), the size of the reconnect burst those imply, and the per-accept time the measurements below would establish. The first two put nine remote committee members on each swarm and eighteen such pairings on the host, each pairing allowed up to those eight connections: derived from the inputs and that constant, not measured, and a floor rather than a ceiling, because non-committee peers connect too.

If both swarms of a node process meet the same arrivals, each stalls on its own task and neither waits for the other. The node command builds one multi-thread runtime and sets no `worker_threads` (`crates/telcoin-network-cli/src/cli.rs:161-165`), so tokio takes `TOKIO_WORKER_THREADS` if the operator sets it and otherwise `available_parallelism()` (`tokio-1.53.1/src/runtime/builder.rs:2008`, `loom/std/mod.rs:88-99`), which on the reference deployment's 8 CPUs is eight worker threads for the whole process: derived, not measured. A worker thread runs a task's poll inline (`worker.rs:689`), so a poll that does not return holds that thread, and two stalled swarm tasks would hold two of the eight while everything else in the process runs on the rest; what then waits is not the runtime but every caller awaiting a reply from either swarm.

## Measurements that would affect the decision

**Task yields and command age under sustained arrivals.** Not run, and decisive. On a reference host running one node process with both its swarms (see Background), drive one swarm's listener over a sweep spanning the container-bridge harness's degradation onset (5,000–10,000 per second) and collapse (75,000–100,000). Record, for both swarms of that process, in `ConsensusNetwork::run`, the interval between yields and the age of the oldest queued command; in the behaviours, the heartbeat's and sweep's tick intervals (`peers/behavior.rs:185`, `stream/behavior.rs:361`); from an established peer, gossip delay and round-trip time. Between them those readings have to tell three things apart: a task that stops returning to the runtime, a command that waits although the task is still returning, and a peer that is slower for a reason outside this process. If the first two grow with arrival rate on the driven swarm while those ticks slip, this task is implicated; if they stay flat while the peer degrades, what serializes is elsewhere; if neither moves at any sustainable rate, nothing here changes. The undriven swarm's figures separate a stall on the task that is being driven from one the whole process shares. The same run serves {{quic-initial-unvalidated-cost}}, {{endpoint-driver-contention}} and {{single-inbound-socket}}, with columns of their own, so it happens once.

**Time on the swarm task per accepted attempt.** Never measured. Its reciprocal is the arrival rate above which the task stops yielding, turning the run above into a checkable rate. On the same host, read it across the swarm branch of `ConsensusNetwork::run` (`consensus.rs:775`), which brackets the accept together with the swarm's own polling; report a distribution rather than a mean, with the node idle and again at each rate of the sweep above. The idle reading is what that branch costs with no attempt arriving, so the accept's share is the difference between the two, and both readings come from code this repository owns. If the reciprocal of that time falls at or below the onset band, the rate at which this task stops yielding is one the bridge harness already reached and the run above should show it there; if it sits well above the collapse band, this task is not what binds at any rate that harness produced; if the time does not move with arrival rate and its reciprocal stays above every rate the sweep reaches, nothing here changes. The per-handshake CPU figures that exist measure a whole handshake in process on superseded versions — a full inbound QUIC+TLS handshake from an unknown peer cost the server 285.8 µs of CPU at the median and 319 µs at the 99th percentile, measured by an in-process benchmark that drove the real libp2p TLS client and server configurations on one desktop-class Intel CPU with `libp2p-tls` 0.6.2 and `rustls` 0.23.37 on the ring crypto provider, where the absolute microseconds run high because CPU frequency could not be pinned, and not reproduced on current versions — a different quantity from the time one accept holds this task.

**An honest full-committee reconnect.** Not run. Restart all ten validators of the reference deployment at once and record first-dial-to-established time, gossip delay and round-trip time beside the counters above; those times also depend on the network between validators, which the reference deployment does not specify. Run it on `main` first. If the burst leaves the yield interval and the command age flat, and the three times stay within what the same figures show with the committee already up, an honest reconnect does not reach this path and the second Goal item's tolerance can be set from what this run records. If the honest burst alone moves the yield interval or the command age, what the first Goal item asks to bound is not particular to a flood, and any bound has to leave room for a reconnect the node is meant to survive. If the three times move while both counters stay flat, what the burst costs sits outside this task and the run bounds nothing here.

Two flood harnesses disagree; both are recorded, neither reconciled. Across a container bridge, against a server with a 212 KB socket receive buffer and no address validation, an established connection began to degrade between 5,000 and 10,000 forged connection attempts per second — its 256-byte echo tail latency at the 99th percentile rising from about 2.4 ms to about 24 ms while every request was still answered — and at 100,000 per second and above a fresh peer could not connect at all, its dial timing out after 10 s, putting the collapse point between 75,000 and 100,000; on loopback it was unaffected to 100,000 malformed attempts per second and collapsed at 175,000, a flood only a quarter of whose packets reached connection-state allocation, so a flood of well-formed attempts, every one of which reaches that point, is dearer per packet and its collapse threshold plausibly lower. Both ran on one desktop-class Intel CPU with libp2p 0.56.0 and `quinn-proto` 0.11.14 against a server built on the libp2p stack, not this node, and neither is reproduced on current versions; the bridge flood forged connection identifiers rather than source addresses. Through every bridge rate the server's CPU stayed below about 1.5 of its 3 cores, so it was not CPU-saturated when it stopped accepting connections: something serialized, and neither harness says whether it was this task, quinn's endpoint state ({{endpoint-driver-contention}}) or the socket's queue ({{single-inbound-socket}}).

## Open questions

- **What is the network between validators?** The reference deployment names the hosts and the committee but not the link speed or the round-trip times (see Background), and several of the figures the runs report are network-bound: the gossip delay and round-trip time recorded under **Task yields and command age under sustained arrivals**, and the first-dial-to-established time that sets the second Goal item's tolerance under **An honest full-committee reconnect**. The maintainers supply it, and it binds the siblings that need the same run, {{quic-initial-unvalidated-cost}}, {{endpoint-driver-contention}} and {{single-inbound-socket}}.
- **Has a validator ever stalled this way?** The Problem is read off the code and has never been seen on a running node, which is why the first Goal item's baseline is the absence of both counters rather than a figure. A stall leaves a thin trace: `wait_for_network_peers` logs only every tenth retry (`crates/node/src/manager/node/start_epoch.rs:973-974`), and while a reply is pending the counter does not advance, so what an operator would have seen is that line ceasing, or never appearing, with no fatal exit after it. It would be settled by the maintainers searching node logs and epoch-start records for that pattern, or by the counters the first Goal item asks for.
- **What does an honest peer do when its dial passes its own deadline with no reply?** The hazard above about an attempt that waits longer than it does today turns on the answer, and so does how far the second Goal item's tolerance can stretch during a mass reconnect or an epoch change. It would be settled by exercising a listener against stock dialers of this release and the previous one, the coverage {{quic-listener-interop-tests}} describes.
- **Do the container-bridge bands hold for this node on current versions?** The sweep under **Task yields and command age under sustained arrivals** and the decision rule of **Time on the swarm task per accepted attempt** are both expressed against that harness's onset and collapse bands, and those bands were measured against a different server on superseded versions, as the figures above record. If the bands sit elsewhere for this node, the sweep and the rule move with them. The same run re-establishes them on the way to its own result.
