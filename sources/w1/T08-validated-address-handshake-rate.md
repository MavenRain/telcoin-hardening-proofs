## Problem

Nothing counts or bounds how fast inbound handshakes begin. Three limits stand between a remote and an established connection, none of them a rate: eight established connections per peer (`crates/network-libp2p/src/consensus.rs:124`, `:136`); a gate on the connected-or-dialing count against `max_peers()` (`crates/network-libp2p/src/peers/manager.rs:604-613`, `peers/behavior.rs:267`); and three `PeerId`-keyed rate limiters running on established connections (`manager.rs:628`, `:1092`, `stream/behavior.rs:262`).

The per-peer limit and the rate limiters are keyed on an identity the dialer picks for itself; the gate on the connected-or-dialing count is the global one. The identity key a `PeerId` hashes signs only the libp2p extension inside the peer's certificate, which is self-signed with a separately generated ECDSA P-256 key (`libp2p-tls-0.7.0/src/certificate.rs:97-98`, `:102`, `:110-114`), so a fresh identity costs two keypair generations and a signature.

The one check keyed on an address is the pending-inbound hook, `handle_pending_inbound_connection`, which takes no `PeerId` and only calls `sanitize_ip_addr` (`crates/network-libp2p/src/peers/behavior.rs:77-85`), reading a ban table an address enters once more than one banned peer is recorded there (`banned.rs:20`, `:125-127`). Those records are written when a connection establishes (`all_peers.rs:566`, `peer.rs:272-277`), so an address holds no state until two identities have completed handshakes there and been banned.

A host with real addresses can therefore start handshakes as fast as it sends them, under a new identity each time, while the node pays a handshake's CPU and connection state for each. Established inbound connections are counted per swarm and direction (`crates/network-libp2p/src/metrics.rs:154-160`, `peers/behavior.rs:253`), but nothing counts handshakes begun, so their rate has never been observed.

## Goal

- **Inbound handshake starts are visible at the node.** A count of handshakes begun, exported per listener and per source address, read against the established count, together with the time an established connection took from the attempt to establishment. *Observable:* the start count, the established count and that time. *Baseline:* of the three, only the established count exists, the one the Problem names; starts are counted nowhere, so that ratio has no denominator, and the `established_in` duration the swarm attaches to every connection it establishes (`libp2p-swarm-0.48.0/src/lib.rs:176-177`, `libp2p-swarm-0.48.0/src/connection/pool.rs:771`) is discarded.
- **What inbound handshake starts cost the node is bounded, or shown not to need bounding.** The CPU and connection state spent on them stay under a bound the maintainers set from *what one commodity host sustains* below; if that measurement finds the cost does not rise with the rate before the link is the constraint, the recorded finding that no bound is needed satisfies this item instead. *Observable:* the counts of the item above read against the node process's CPU time over one run, taken as the difference against a run of the same length with no inbound starts, since one process runs both swarms and the rest of the node's work. *Baseline:* no measured baseline exists; *what one commodity host sustains* sets it.
- **Honest peers unaffected.** With every committee member reconnecting at once, no honest handshake is refused, and the time from a dial to an established connection stays inside the distribution *the honest peak* below records while no bound is in place, including while committee membership for a new epoch is still resolving (`crates/network-libp2p/src/peers/manager.rs:899-906`). *Observable:* a reconnect test across the committee of ten on the reference deployment (see Background), every node process running both its swarms, repeated across a committee change with membership withheld; each node reports the dial-to-established time of the first item above. *Baseline:* *the honest peak* below sets it; nothing records that distribution today.
- **Non-goals.** Sources that cannot complete a round trip ({{quic-initial-unvalidated-cost}}). How a swarm accounts for the handshakes it is holding unfinished ({{pending-inbound-unbounded}}). What an established peer may do. Surviving a link-saturating flood. Refusing identities the node does not recognise: it refuses only its own and banned ones today (`peers/behavior.rs:87-107`), so counting only those would count almost nothing ({{late-refusal-of-strangers}}).
- The issue closes when starts are counted and exported per listener and per source address, the dial-to-established time is recorded, *the honest peak* and *what one commodity host sustains* are taken and recorded with their setup, and the maintainers have either set a bound from them or recorded that none is needed.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

Nothing here that acts inside the node before a handshake begins can be acted on until {{quic-initial-unvalidated-cost}} is: the listener performs no address validation today — `libp2p-quic` accepts every incoming attempt unconditionally (`libp2p-quic-0.14.0/src/transport.rs:595`) and nothing in the crate calls quinn's retry, refuse or ignore. A validated address is one a round trip has proved the sender receives packets at (RFC 9000 section 8.1). Counting the starts does not wait on it.

Validation would not separate this population from honest peers. RFC 9000 section 8 states its purpose: "Address validation ensures that an endpoint cannot be used for a traffic amplification attack." A rented host passes it. `quinn-proto` can bind a source address into a token with a 15 s lifetime that reaches the dialer in a retry packet (RFC 9000 section 8.1.2), at the cost of a round trip honest dialers do not pay today (`quinn-proto-0.11.18/src/token.rs:286-293`, `config/mod.rs:242`). Connection migration is off (`libp2p-quic-0.14.0/src/config.rs:162`), so a connection keeps the address it established on.

### Approaches surveyed so far

**Budget on handshake starts keyed on the source address, or a prefix of it.** Starts are counted against the address an attempt arrives from, or against a block of addresses containing it, and that count decides whether a start proceeds. A host commonly controls an IPv6 /64, so rotating inside its own allocation costs nothing (#956), and a prefix wide enough to cover one shares a key with NAT and cloud egress pools.

**Ceiling on handshake starts across the listener, not keyed at all.** One count for the whole listener decides whether a start proceeds, whatever it arrived from. Nothing in the ceiling tells an attempt from a rented host from a committee member's, so the share that arrives first is the share honest peers lack.

**Exempting committee members' addresses from whatever bound applies.** The addresses the node associates with current members are left out of whatever count the bound reads, so their starts proceed at whatever rate they arrive. Membership is keyed by `BlsPublicKey` and members whose network identity is unknown resolve asynchronously (`manager.rs:899-906`), so the set lags an epoch change, and an exemption on an address that has not completed a round trip rests on a value the sender chose.

**Per-source rate limiting at the provider edge or the host firewall.** Starts are capped per source before the packets reach the node, by a rule the operator configures there. That rule applies to whatever reaches that edge and to nothing else, while the acceptance rules above require a defence that holds when the host firewall is absent or wrong.

**Puzzle the dialer answers before the handshake proceeds.** The server asks the dialer for work it has to complete and return before the handshake goes on. Nothing in QUIC or libp2p carries an answer a dialer computed: a dialer's response to a retry packet is to check its integrity tag and resend the same ClientHello with the server's opaque token (`quinn-proto-0.11.18/src/connection/mod.rs:2478-2506`) ({{quic-listener-interop-tests}}).

Each entry above that would act inside the node before a handshake begins meets the question {{quic-initial-unvalidated-cost}} covers, what an inbound connection attempt costs the node before any node code decides on it; where acting there means a modified transport crate, it meets {{patched-transport-crate-upkeep}} too.

## Implementation details to pay close attention to

- If accounting is keyed on a source address before that address has completed a round trip, the key is attacker-chosen: an attempt can carry an honest validator's address and spend what is attached to it.
- If honest peers share a key they share its consequences: every swarm a host runs listens on its own socket but sits behind one address (two swarms per host on the reference deployment), and NAT and cloud egress pools put unrelated peers behind one address too, so a bound each of them would stay under on its own is crossed by their sum.
- If the table that holds the accounting is unbounded, it is itself the resource under attack: the number of distinct keys a remote can present is bounded by the identities it can mint, two keypair generations and a signature each, or by the addresses it holds, and the node controls neither; a count exported per source address is such a table.
- If a decision is taken before the `PeerId` is known, today's exemption cannot inform it: `peer_is_important` takes a `PeerId` (`manager.rs:894-897`).
- If the input a defence reads is empty or still resolving at a committee change, and it does not admit while unresolved, an address change becomes a partition.
- If anything new is visible on the wire, a peer on the previous release dials with a stock `libp2p-quic` and can neither signal nor answer it, seeing only an ordinary connection outcome.
- If an honest mass reconnect after a restart or a partition heal crosses whatever bound is set, honest handshakes are refused while the network recovers; the inputs that bear on where any such bound would sit are committee size (ten on the reference deployment), connections per peer, reconnect burst size and swarms per host (two there).

## Measurements that would affect the decision

**The honest peak**, never measured. Inbound handshake starts per second, and per source address, that honest traffic produces at its worst — a restart, a partition heal, an epoch change — on the reference deployment (see Background), together with the time from dial to established connection over the same run. What the run has to distinguish is starts from the connections that reached established, and starts from one another by the address they arrived from. All three readings are available to node-owned code today: the behaviour is told of every pending inbound connection together with its remote address, before the handshake proceeds (`crates/network-libp2p/src/peers/behavior.rs:77-85`); established connections already have the counter by direction the Problem names; and the time is `established_in`, which the swarm attaches to every `SwarmEvent::ConnectionEstablished` as the interval from the attempt entering the connection pool to the connection being established (`libp2p-swarm-0.48.0/src/lib.rs:176-177`, `libp2p-swarm-0.48.0/src/connection/pool.rs:771`) and which this node discards today. The maintainers still supply the network between the validators, and their records show how many members share a source address. Committee members put a floor under the starts and not a ceiling: nine remote members per swarm and two swarms per node process give eighteen inbound starts per host in a full reconnect at one connection per member, before any retry and before non-committee peers, with the per-peer limit the Problem names permitting eight to each of them, while the gate on the connected-or-dialing count is a comparison against `max_peers()`, 39 on defaults (30 target peers, from `K_VALUE / 2 + K_VALUE` with kad's `K_VALUE` of 20, raised by the 0.3 excess factor and rounded up: `crates/config/src/network.rs:468`, `:474`, `:489-491`, `libp2p-kad-0.49.0/src/lib.rs:91`); because it compares with `>=` (`crates/network-libp2p/src/peers/manager.rs:611`) after the new connection is registered (`peers/behavior.rs:249-252`, the gate at `:267`), it retains at most 38 peers per swarm and so 76 across the two swarms of one host, with committee members and operator-allowlisted peers exempt from that gate (`crates/network-libp2p/src/peers/manager.rs:894-897`). Both counts are derived from the reference deployment, not measured. If the peak sits far below what one commodity host sustains, the two populations differ in the rate a single address produces, which is the difference the entries keyed on the source or on a prefix of it would read; if they are close, or honest peers sit behind shared addresses widely enough that no peak attaches to one, they do not differ that way, and whatever separates them has to come from something other than the address.

**What one commodity host sustains**, never measured. Handshake starts per second one rented host with real addresses can make a listener begin, against a node on the reference deployment, swept upward from the honest peak until the CPU time the node spends per start stops holding steady or honest dials take measurably longer to reach established. The instruments are the three *the honest peak* reads, `established_in` standing here for what an honest dialer sees. The CPU time a start costs is read as the node process's CPU time over the run, less its CPU time over a run of the same length and otherwise alike with no inbound starts, divided by the starts counted, because that one process also runs both swarms and the rest of the node's work. Every attempt in this run completes a round trip from an address that receives the reply. If the sustained rate sits far above the honest peak and the node's CPU rises with it, the two rates differ by that gap and the gap is what a bound would be set from; if it sits near the honest peak, no bound on the rate separates the two populations and whatever separates them has to come from something other than the rate; if handshake CPU does not rise with the rate before the link itself is the constraint, nothing here needs a bound and the counts and the time the first Goal item asks for are all this issue produces.

**What one inbound handshake costs the server**, measured once, not reproduced on current versions. A full inbound QUIC+TLS handshake from an unknown peer cost the server 285.8 µs of CPU at the median (319 µs at the 99th percentile), measured by an in-process benchmark that drove the real libp2p TLS client and server configurations on one desktop-class Intel CPU with `libp2p-tls` 0.6.2 and `rustls` 0.23.37 on the ring crypto provider. That figure covers key generation, the X25519 agreement, the server's own `CertificateVerify` signature, its whole flight, and the roughly five signature verifications `rustls` performs across two parses of the client certificate; client-side CPU is excluded and client session resumption was off, since an unknown peer holds no session ticket. The absolute microseconds run high because the benchmark could not pin the frequency governor or turbo while the timer ticks at the nominal clock, so ratios within the run hold where the absolute values do not; it ran in process, with no socket, no kernel path and no concurrency, on one host and one CPU model. The branch resolves `libp2p-tls` 0.7.0 on the `aws_lc_rs` provider and `quinn-proto` 0.11.18, so the figure prices a pair of versions this branch does not run: a lower cost per handshake means a rented host has to make more starts before the node's CPU moves and a higher one means fewer, and either way it prices what a start commits the node to rather than the rate at which starts arrive, which is what the two runs above measure.

No per-source bound has been measured: the two existing harnesses forged connection identifiers rather than source addresses, because the environment would not forward forged sources, and neither added a per-source limit, so no approach above has a measured effect. An attacker with many source addresses would defeat a per-source limit, and that case is untested. Neither harness ran on a real network interface with receive offload, and nothing has been measured behind a provider edge that caps such traffic, so the two runs above have to be taken on production-class hardware rather than inferred from either.

## Open questions

- **Is the node to refuse identities it does not recognise?** No such policy exists: the node refuses only its own identity and banned ones, as the non-goal above says with its citation, so every start these counts would cover comes from a peer the node admits today, and that non-goal, which says a count limited to the identities the node refuses would count almost nothing, depends on it staying true. A decision for the maintainers, and one no issue here settles; shared with {{late-refusal-of-strangers}}.
- **Do the two rates overlap?** The second Goal item asks for a bound on what inbound handshake starts cost the node, or for a recorded finding that none is needed, and the third holds honest dials to what they take today; a bound separates the two populations only if the rate one rented host sustains sits well above the rate honest traffic peaks at. Neither rate has been measured. *The honest peak* and *what one commodity host sustains* settle it together, and each already says which way its result pushes.
- **What network sits between the validators?** The reference deployment fixes the committee, the hosts and the swarms per host, but not the link speed or the round-trip times, and both measurements move with them: how much of the dial-to-established distribution *the honest peak* records is round-trip time rather than work at the node is not known, and neither is whether the link or the node caps first the rate one rented host can sustain. An input the maintainers supply; until they do, neither measurement's numbers carry from one network to another.
- **How many validators share a source address?** A peak attaches to an address only if honest peers do not sit behind shared ones, and the hazard above about honest peers sharing a key turns on the same fact; the reference deployment names the hosts but not the provider or the addressing in front of them. The maintainers' deployment records settle it, and the per-source column of *the honest peak* shows what the running network actually does.
