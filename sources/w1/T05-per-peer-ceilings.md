## Problem

An **established** connection has finished its handshake and its `PeerId` is known to the swarm. `PeerId`s are free to generate, so every ceiling below is keyed on something the remote mints, and one identity may hold their product on one swarm:

| Ceiling (per connection unless stated) | Value | Where set |
|---|---|---|
| Established connections per `PeerId`, both directions | 8 | `crates/network-libp2p/src/consensus.rs:124`; rationale at `:119-123`; counted "regardless of direction (incoming or outgoing)" (`libp2p-connection-limits-0.7.0/src/lib.rs:223-224`) |
| QUIC inbound bidirectional streams | 10,000 | `crates/config/src/network.rs:403` → `libp2p-quic-0.14.0/src/config.rs:146` |
| QUIC window credit, connection / stream | 100 / 50 MiB | `network.rs:407-408` → `config.rs:152-153`; comment at `:406` |
| Request-response streams, per behaviour, two per swarm | 100 | `libp2p-request-response-0.30.0/src/lib.rs:319` via `Config::default()` (`consensus.rs:455`, `:466`) |
| Inbound substreams negotiating | 128 | `libp2p-swarm-0.48.0/src/connection/pool.rs:1020`, not overridden (`consensus.rs:577-581`) |
| Kademlia inbound substreams | 32 | `libp2p-kad-0.49.0/src/handler.rs:48`, enforced `:521` |

Multiplied by the 8: per identity per swarm, 80,000 QUIC stream credits, 800 MiB of window credit, 1,600 request-response streams, 1,024 substreams in negotiation, 256 Kademlia substreams. Windows and stream counts are credit advertised, not memory allocated: bytes go resident as the peer sends and the application has not read (`quinn-proto-0.11.18/src/config/transport.rs:106-121`). quinn states what the credit prices (`:66-67`): "Worst-case memory use is directly proportional to `max_concurrent_bidi_streams * stream_receive_window`, with an upper bound proportional to `receive_window`."

What bounds the identities is the peer-count gate, `max_peers()` at 39 on defaults (`peer_excess_factor` is 0.3 at `crates/config/src/network.rs:474`, and `:489-491` multiplies the target of 30 at `:468` by one plus that factor, 1.3, then takes the ceiling): compared with `>=` after establishment, answered by a graceful disconnect, not a refusal (`peers/behavior.rs:266-272`), and bypassed for validators and operator-allowlisted peers (`peers/manager.rs:894-897`). The arriving connection is registered before the check runs (`peers/behavior.rs:247-263`, check at `:267`), so the count compared with `max_peers()` already includes the new identity (`peers/manager.rs:611`): whoever makes that count reach 39 is the one disconnected, so the gate holds the identities it can refuse to 38. It refuses none of the bypassed ones, which are retained on top of that 38 whenever they arrive with the count already full. At 38 identities, one swarm's worst case is 304 connections, 3,040,000 stream credits and about 29.7 GiB of window credit, and every bypassed identity past them adds its own eight connections to that.

So whoever mints identities decides how much of the node's memory and per-connection task state is spoken for, and no figure here is anchored to honest need. Only the 8 has a derivation, and it argues from expected use rather than from measurement (`consensus.rs:119-123`): "a peer needs at most one inbound and one outbound connection concurrently (this node dials with `PeerCondition::Disconnected`, so it does not stack redundant outbound dials), and brief reconnection churn adds only a small transient overlap. Eight leaves room for that churn while bounding a hostile peer to a fixed, small number of connections instead of an unbounded fan-out." Nobody has measured what an honest peer holds at peak, so no ceiling here can be called too high or too low today. The peer-count gate is in scope here only as the multiplier on that product: where an identity-keyed refusal sits, and whether an unknown, unbanned identity should be refused at all, belongs to {{late-refusal-of-strangers}}.

## Goal

- **What one identity may hold is bounded against observed honest need.** The most one identity may hold is a figure the maintainers set against the honest peak that **Honest peak occupancy** records below. *Observable:* a test in which one identity opens as much as the node permits reports what it was granted (connections, streams and window credit) and asserts each against the recorded peak, whatever accounting produced the grant. *Baseline:* the product above, against an unrecorded peak.
- **Memory one identity can hold is bounded.** Peak resident bytes attributable to one identity holding the ceilings above stay within a bound the maintainers set from **Memory held by one identity at the ceiling** below. *Observable:* that measurement reports the peak per identity per swarm, and the per-peer connection counts the node already keeps, described under **Honest peak occupancy**, show on a running node whether any identity is at the connection ceiling the figure was measured at. *Baseline:* the measurement described below sets it; what is on record today is advertised credit, 800 MiB per identity per swarm, not bytes held.
- **Honest peers unaffected.** With every committee member reconnecting at once and catch-up traffic in flight (catch-up being a lagging node's fetch of the certificates it missed, `crates/consensus/primary/src/certificate_fetcher.rs:1`), no honest request is dropped at capacity and completion stays within what **Catch-up completion across window values** records, to a tolerance set with it. *Observable:* a multi-swarm reconnect test, on the reference deployment (see Background), asserts the `WARN` line "Dropping inbound stream because we are at capacity" (`libp2p-request-response-0.30.0/src/handler.rs:169`) is never emitted. *Baseline:* the drop count is checkable today; that measurement sets the completion time.
- **Non-goals.** How a swarm accounts for inbound connections whose handshake has not finished ({{pending-inbound-unbounded}}); handshake rate from an address that can complete a round trip ({{validated-address-handshake-rate}}); where a refusal sits ({{late-refusal-of-strangers}}); moving bulk exchanges off request-response (#739); surviving a link-saturating flood.
- The issue closes when the peak occupancy and memory figures are recorded, what one identity may hold is stated in writing against those figures, and both tests named above have run: the grant test of the first item and the multi-swarm reconnect test of the third.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

On that deployment the per-swarm worst case above doubles: two swarms in one process permit 608 established connections, 6,080,000 QUIC stream credits and 60,800 MiB of window credit, about 59.4 GiB or 63.8 GB, against the host's 32 GB of RAM. The factors are the 38 identities the peer-count gate can hold a swarm to (`crates/config/src/network.rs:489-491`, the comparison at `crates/network-libp2p/src/peers/manager.rs:611`), the 8 connections per identity (`consensus.rs:124`), the 10,000 inbound streams (`network.rs:403`) and the 100 MiB connection window (`:408`), with the per-swarm identity count taken twice for the two swarms; the product is derived, not measured, and the credit is advertised, not resident. Nine of the 38 identities on each swarm are the committee's other nine validators, permitted 72 connections and 7,200 MiB of window credit per swarm on the same defaults. Those nine bound nothing: they count toward the 39 but cannot be refused by it, because committee members are recorded as validators (`crates/network-libp2p/src/peers/manager.rs:903`) and validators are exempt from the check (`:894-897`), so with the nine already counted, twenty-nine further peers, none of them in the committee, are retained alongside them and the thirtieth is disconnected (`:604-613`); a validator that connects once the count is full is retained anyway.

The 8 exists because of #1010: without it, one unbanned peer could open connections up to the OS and QUIC file-descriptor and memory limits (`consensus.rs:115-117`). The QUIC values carry no per-identity dimension at all: one `QuicConfig` (`crates/config/src/network.rs:374-411`) applies once per swarm (`consensus.rs:563-574`), so every established connection on a swarm is advertised the same windows, whatever identity holds it. The per-stream value is half the connection value (`crates/config/src/network.rs:407-408`), so two streams written to the full per-stream window exhaust the connection budget between them; keeping the per-stream window below the connection window is what stops one stream monopolizing the receive buffers while the application is not reading it (`quinn-proto-0.11.18/src/config/transport.rs:110-113`).

The request-response ceiling, unlike the QUIC ones, is not signalled on the wire: at capacity the inbound stream is dropped with a log line and, by design, no failure reaches the upper layer (`libp2p-request-response-0.30.0/src/handler.rs:161-169`), so the sender learns nothing until the 10 s timeout (`lib.rs:318`). Inbound and outbound requests to a peer also share one bounded map (`handler.rs:83`, `:113-116`).

### Approaches surveyed so far

Bounding by bytes or work per identity rather than by counts. Constraint: no accounting of that shape exists — `connection_limits` counts connection ids (`libp2p-connection-limits-0.7.0/src/lib.rs:81`), request-response counts streams per connection (`handler.rs:83`), quinn's windows are per connection, never aggregated across an identity.

Different ceilings for different classes of remote. Constraint: the QUIC values are fixed in one `QuicConfig` before any remote `PeerId` exists (`consensus.rs:563-574`); the per-identity dimension the connection-limits layer carries is a bypass set consulted ahead of every established-connection check (`libp2p-connection-limits-0.7.0/src/lib.rs:75`, `:261-263`), an exemption rather than a second set of values; the committee membership a class derives from turns over each epoch and must fail open.

Lowering the inherited numeric ceilings. Constraint: the connections figure has a derivation in source (`consensus.rs:119-123`) a lower figure has to survive; the request-response figure is shared with this node's own outbound requests, with silent overflow, as above; the window values move together and their rationale ties them to round-trip time and throughput (`network.rs:406`); the honest peak is unmeasured.

## Implementation details to pay close attention to

- If a ceiling changes while peers run the shipped value, the two sides do not learn of it the same way: the QUIC ceilings are transport parameters each receiver advertises per connection, while the request-response ceiling has no wire signal, so excess inbound requests are dropped as above and the sender sees only the timeout.
- If a ceiling derives from the committee list, that list is briefly stale or absent at an epoch change, so the value in force at that moment is whatever an empty or outdated list derives to, and the honest peers reconnecting across the change are the ones that meet it.
- If a figure is taken from steady state, it misses the two moments occupancy peaks: the reconnect overlap the 8 exists for, and where catch-up opens the most streams.
- If a change is evaluated on one swarm, it multiplies by the swarms on the host, two on the reference deployment, each with its own `QuicConfig` and limits behaviour.
- If accounting is keyed on an identity, the peer-count gate is no floor under it, for the three reasons the Problem gives.
- If any figure here is set rather than inherited and one of the inputs behind it is missing, the figure rests on something unstated: a maintainer setting it needs the peak that **Honest peak occupancy** records, the size of the reconnect burst that sets that peak, the committee size and the number of swarms on the host (ten and two on the reference deployment), the catch-up throughput the windows have to carry, and the share of the host's 32 GB the transport is allowed to hold.

## Measurements that would affect the decision

**Honest peak occupancy.** Not taken, and the one that matters: peak concurrent connections per `PeerId`, and request-response streams, QUIC streams and Kademlia inbound substreams per connection, across an epoch change and a full-committee reconnect, reported per identity so the spread across identities is visible and not only the largest. The two kinds of count are not equally reachable today. Connections per identity are counted in this repository's own code: the peer store holds `num_in` and `num_out` per peer (`crates/network-libp2p/src/peers/status.rs:13-18`), incremented on the path every established connection already takes (`peers/behavior.rs:247-263`, `peers/manager.rs:724-752`, `peers/all_peers.rs:566-567`, `crates/network-libp2p/src/peers/peer.rs:381` and `:406`); neither counter is decremented when one connection of a still-connected peer closes, so what they give is connections opened while the peer stayed connected, an upper bound on the concurrent figure rather than the peak itself, while the exact concurrent set, the one the 8 is enforced against, sits unexported in `connection_limits::Behaviour` (`libp2p-connection-limits-0.7.0/src/lib.rs:81`, checked at `:269-276`). The per-connection stream counts have no reading from node-owned code at all: the request-response count is in the handler's bounded map (`libp2p-request-response-0.30.0/src/handler.rs:83`), the Kademlia count in that behaviour's own handler, where the 32 is enforced (`libp2p-kad-0.49.0/src/handler.rs:521`), and the QUIC count inside the `quinn::Connection` that `libp2p-quic` keeps in a private field and exposes only as a stream muxer (`libp2p-quic-0.14.0/src/connection.rs:37-39`, `:67`); counting instead the requests the node itself handles would miss the case the ceiling defines, because a stream dropped at capacity is never reported to the upper layer (`handler.rs:161-169`). A run that wants the exact per-connection figures rather than the upper bound therefore reads them from modified copies of those crates, and for as long as it does it depends on the upkeep {{patched-transport-crate-upkeep}} owns. The run uses the reference deployment: a committee of ten and both swarms of one node process, read per swarm. The network between validators is still an input the maintainers supply. If the peak sits well below the figures above, the distance between the two is what any change to them is judged against; if it sits close to them under load, there is little distance, and a figure set near the peak leaves honest traffic no headroom at the moments occupancy peaks; a window catching neither event settles neither.

**Memory held by one identity at the ceiling.** Peak resident memory attributable to one identity holding the ceilings above, read as the difference in the node process's resident set size between a run with that identity at the ceilings and the same run without it, on the reference host of 8 CPUs and 32 GB of RAM. What makes window credit cost bytes is the condition the `stream_receive_window` documentation names, data arriving on a stream the owning behaviour has not read (`quinn-proto-0.11.18/src/config/transport.rs:110-113`), so the run reports two cases: streams open and idle, and streams carrying data the node has not drained. Nothing exports buffered bytes per connection, which is why the figure is a difference between runs rather than a counter; what confirms the identity actually reached the ceilings is the occupancy **Honest peak occupancy** reads, with the limits stated there. If the peak tracks the 800 MiB advertised per identity per swarm, bytes bind first; if it stays far below with the streams carrying data, counts and per-connection task state bind first; if the two runs differ by less than the run-to-run spread of the process's resident set, this measurement settles neither, and telling the two apart would need bytes counted per connection, which nothing exports today.

**Catch-up completion across window values.** Completion time for a lagging node's certificate fetch (`crates/consensus/primary/src/certificate_fetcher.rs:45-49`) on the reference deployment's committee of ten, swept above and below today's window values. It tests their only rationale in source (`network.rs:406`), a throughput never measured. Flat completion means the windows buy throughput nothing uses; a fall-off below today's values means they are load-bearing for honest catch-up, and the value at which the fall-off starts is the floor under any accounting that holds bytes back from a committee member, whether that accounting is one value per swarm, one value per class of remote or a budget per identity. The round-trip times and the path it runs over are still inputs the maintainers supply, because the network between validators has not been specified.

Nothing measures what an established peer occupies under load. The nearest figure on record is the size of the structures themselves: the QUIC library's connection struct measured 6,016 bytes and its endpoint struct 688 bytes on x86_64, printed from a compiled program against `quinn-proto` 0.11.14, struct sizes only, excluding the TLS handshake state, the connection-identifier index entry and the per-connection task a live connection also holds, and not reproduced on current versions.

## Open questions

- **Is the peer-count gate, `max_peers()` at 39 on defaults, meant to be the standing bound on how many distinct identities can hold these ceilings at once?** The node-wide arithmetic in the Problem and the per-host figures in Background both take the 38 identities it can hold a swarm to as the multiplier, and the first Goal item bounds a product that multiplier scales; how the check behaves is stated in the Problem, and source calls it the maximum number of peers allowed to connect to this node (`crates/config/src/network.rs:488`), but nothing in source says whether that description is meant to hold as a standing bound on the identities that hold these ceilings. A decision by the maintainers settles it.
- **What link speed and round-trip times separate validators on the reference deployment?** **Honest peak occupancy** records what a full-committee reconnect actually opens and **Catch-up completion across window values** sweeps window values whose only rationale in source is round-trip time and throughput (`crates/config/src/network.rs:406`), and both change shape with the network they run over. It is an input the maintainers supply, and every issue in this set whose measurements run on the reference deployment needs the same one.
- **Should a remote whose `PeerId` is in no committee the node tracks and is not on the operator's allowlist be admitted to these ceilings?** Every ceiling here is keyed on an identity, so the answer decides whether the multiplier on the product is the peer-count gate or the committee plus the allowlist, and an approach giving different classes of remote different ceilings needs a class the node does not define today. No such policy exists; {{late-refusal-of-strangers}} owns where that decision would be made.
- **What share of the reference host's 32 GB may this transport hold at peak?** The memory item in the Goal asks for a bound set from **Memory held by one identity at the ceiling**, but that measurement reports one identity on one swarm, and turning it into a ceiling needs a figure for the whole transport across both swarms of a process that has other claims on the same memory. A decision by the maintainers settles it; no measurement here does.
