## Problem

`libp2p-quic` accepts every incoming QUIC connection attempt unconditionally: the listener's only branch is whether `accept()` itself returned an error (`libp2p-quic-0.14.0/src/transport.rs:595-599`). Inside `quinn_proto::Endpoint::accept` (`quinn-proto-0.11.18/src/endpoint.rs:549`) the server decrypts the Initial (`:601-605`) — the first packet of a connection attempt, at least 1,200 bytes, carrying the TLS ClientHello (RFC 9000 section 14.1) — starts a `rustls` session (`:645`), builds the whole `quinn_proto::Connection` (`:647`) and runs that packet synchronously (`:665`), so rustls emits the server's whole first flight: an ephemeral key agreement (`rustls-0.23.37/src/server/tls13.rs:502`) and a certificate signature (`:787`). All on the swarm task, which also polls every behaviour of that swarm, and all before the node's first hook, `handle_pending_inbound_connection` (`libp2p-swarm-0.48.0/src/lib.rs:955-959`), implemented at `crates/network-libp2p/src/peers/behavior.rs:77-85`, which sees a multiaddr and nothing else.

None of it depends on the sender receiving the reply. A validated address is one the server has evidence the sender can receive packets at, because a round trip through it completed (RFC 9000 section 8.1); a forged source never gets there, and QUIC's anti-amplification limit caps only the bytes sent back to it (`quinn-proto-0.11.18/src/connection/paths.rs:159-160`).

So every attempt, whatever its source, commits two asymmetric operations and a connection's worth of memory on the swarm task before the node has a say. That cost has never been measured under load: no forged-source flood has been run on any hardware, and the floods that were run forged connection identifiers instead and disagree.

## Goal

- **A flood from sources that cannot receive a reply does not cost the node its committee traffic.** With such attempts arriving at every swarm at once, an established peer's latency and a fresh peer's ability to connect stay inside a bound the maintainers set from **Forged-source flood on production-class hardware** below. *Observable:* that run's latency and fresh-dial columns across its sweep. *Baseline:* unmeasured for forged sources; that run sets it.
- **How incoming attempts ended is visible on a running node,** so a change's effect and any regression show up in production. *Observable:* per-listener counters separating attempts that became established connections from attempts that ended without one, with the reason for the second group wherever the node is given one. *Baseline:* none — `crates/network-libp2p/src/metrics.rs` declares fourteen metrics, none about an incoming attempt.
- **Honest peers unaffected, as the regression guard.** With a whole committee reconnecting at once — restart, healing partition, epoch change — no honest handshake is refused and first-dial-to-established time stays inside a tolerance the maintainers set from the reconnect columns of **Forged-source flood on production-class hardware**, flood on and off. *Observable:* a reconnect test on the reference deployment (see Background), all ten validators at once and both swarms of each node process.
- **Non-goals.** Packets reaching the socket ({{single-inbound-socket}}); the handshake rate from addresses that do complete a round trip ({{validated-address-handshake-rate}}); what an established peer may do ({{per-peer-ceilings}}); any volumetric control.
- **What closes this issue:** the **Forged-source flood on production-class hardware** run and its numbers, the counters in a release, and the bound each item above is held to, written down. Where that run shows degradation inside its sweep, closing it also takes the run repeated after whatever change is made, with its columns inside those bounds.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

Work before `accept()` runs on quinn's endpoint driver, the background task that reads one endpoint's socket and queues new attempts (`quinn-0.11.9/src/endpoint.rs:361-367`), where a queued attempt begins as an empty buffer entry (`quinn-proto-0.11.18/src/endpoint.rs:521-525`). quinn can dispose of an attempt otherwise — `Incoming` offers `accept()`, `refuse()`, `retry()` and `ignore()` beside `remote_address_validated()`, and the endpoint counts handshakes accepted, refused and ignored (`quinn-0.11.9/src/incoming.rs:27-93`, `endpoint.rs:338-346`) — but `libp2p-quic` reaches none of it: `QuinnConfig` is `pub(crate)` (`libp2p-quic-0.14.0/src/config.rs:121`) and the crate sets only the transport configuration (`:158`) and `migration(false)` (`:162`) on quinn's `ServerConfig`. A retry answers the Initial with a token instead of a handshake: the sender has to repeat that token in its next Initial, and returning it is what proves the sender can receive packets at that address (RFC 9000 section 8.1.2); quinn seals the client's address and the connection identifier from its first packet into the token it issues (`quinn-proto-0.11.18/src/token.rs:286-293`).

So quinn's bounds on attempts awaiting acceptance sit at their defaults, per endpoint and so per swarm: `max_incoming`, 65,536 attempts held between queueing and acceptance (`quinn-proto-0.11.18/src/config/mod.rs:251`); `incoming_buffer_size`, 10 MiB buffered per waiting attempt (`:252`); `incoming_buffer_size_total`, 100 MiB across them (`:253`); a 15 s address-validation token lifetime (`:242`). Since `quinn-proto` 0.11.15 (`quinn-rs/quinn` PR #2683) an Initial arriving while `max_incoming` is full is ignored before Initial keys are derived and draws no reply (`endpoint.rs:455-461`, keys `:463`), honest ones included. On the reference deployment each host runs two of those endpoints, so today's defaults permit 131,072 attempts awaiting acceptance per host (65,536 × 2) and 200 MiB of buffered Initial data (100 MiB × 2) against the host's 32 GB of RAM. Those two figures are derived from the defaults and the reference deployment, not measured.

### Approaches surveyed so far

- **Carry a modified copy of `libp2p-quic`** with a decision point ahead of `accept()`; that is how any approach here acting at that point reaches the code. Constraint: pinning it, matching advisories and rebasing on each libp2p bump have no process here ({{patched-transport-crate-upkeep}}).
- **Drive quinn directly.** Constraint: `libp2p-quic` also supplies `PeerId` extraction (`libp2p-quic-0.14.0/src/connection/connecting.rs:55`), muxer glue (`connection.rs:67`) and hole punching (`lib.rs:65`), and rebuilding those is uncosted.
- **Filter at the host firewall or the provider edge.** Constraint: a stateless filter cannot tell a forged-source Initial from an honest first contact — both are datagrams of at least 1,200 bytes from unfamiliar addresses (`quinn-proto-0.11.18/src/lib.rs:330`) — and what an edge strips is unknown here.
- **Issue `NEW_TOKEN` tokens so a returning peer skips the round trip** (RFC 9000 section 8.1.3). Constraint: quinn's client token store is keyed by server name (`quinn-proto-0.11.18/src/token_memory_cache.rs:29-30`) while `libp2p-quic` dials every peer under the one name `"l"` (`transport.rs:306`), so a dial usually presents another server's token; a per-peer store is untried.
- **Lower quinn's bounds on attempts awaiting acceptance.** Constraint: `libp2p_quic::Config` exposes none of them (`libp2p-quic-0.14.0/src/config.rs:30-60`), the one open upstream change to QUIC configuration (`libp2p/rust-libp2p` #6182) adds none, and at the bound the behaviour is the silent drop above; the rate a lower one would bite at is unmeasured.
- **Send a retry packet to a source that has not completed a round trip** (RFC 9000 section 8.1.2), through quinn's `retry()`, which discards the waiting attempt and seals a token binding that address (`quinn-proto-0.11.18/src/endpoint.rs:752`, `:763-768`). Constraint: one extra round trip per such connection, unmeasured on a long path; `libp2p-quic` offers no place to call it; and running it only above a load threshold makes the attacker's arrival rate the input, on a path no test covers.
- **Upstream a decision point into `libp2p-quic`.** Constraint: nothing of the kind is open — searches of `libp2p/rust-libp2p` issues and pull requests on 2026-09-19 for QUIC retry, incoming connections and address validation found nothing bearing on one — and how one would be received is untested.

## Implementation details to pay close attention to

- If accounting is keyed on a source address before that address has completed a round trip, the key is attacker-chosen; quinn reports whether that round trip has happened (`quinn-0.11.9/src/incoming.rs:78-85`), and if a completed round trip is then treated as a scarce identity, one host with an IPv6 /64 supplies 2^64 ({{validated-address-handshake-rate}}).
- If a bound is set per endpoint it is per swarm: each swarm builds its own `ServerConfig` (`libp2p-quic-0.14.0/src/config.rs:157`) with its own `max_incoming`, buffer total and token key, the key random per `ServerConfig` (`quinn-proto-0.11.18/src/config/mod.rs:395-396`), so nothing sealed under it survives a restart. Lower such a bound and an honest peer that meets it sees only a timeout.
- If a bound is ever given a number, the inputs it takes are the committee size, the eight established connections each peer may hold (`crates/network-libp2p/src/consensus.rs:124`, applied at `:136`), the size of an honest reconnect burst and the host's memory budget divided across its swarms.
- If first contact comes to cost an extra round trip, a restart, a healing partition and an epoch committee change each pay it for every peer at once; and if honest peers are then refused or delayed, the 120 s wait for an established peer that epoch start runs on each swarm expires on the swarm that has none and the node process exits (#1398). If a decision consults a committee or address list, that list can be stale when it matters and honest peers still have to connect.
- If a decision is added anywhere the listener is polled, it runs on the swarm task beside every behaviour of that swarm ({{accepts-unbounded-per-poll}}, {{endpoint-driver-contention}}), and without counters for how attempts ended neither its effect nor a regression is visible in production.
- If the listener's behaviour changes, peers dialling it stay on stock crates of libp2p 0.57.0 and of the 0.56.0 release before it while the fleet is mixed, and no test exercises this listener against a dialer of either ({{quic-listener-interop-tests}}).

## Measurements that would affect the decision

**Forged-source flood on production-class hardware.** Not run. Drive both swarms of one node process with attempts whose sources cannot receive a reply, on the reference deployment (see Background), sweeping arrival rate from below the 5,000–10,000 attempts per second at which an established connection began to degrade in the container-bridge run described below (not reproduced on current versions) past that run's 75,000–100,000 collapse band. Per swarm report listener CPU, memory held for attempts that never established, an established peer's latency and whether a fresh peer connects, the last two repeated with the whole committee of ten reconnecting, flood on and off. Both swarms run in one process, so listener CPU has to be attributed to each swarm's task; where nothing on the host attributes it, the run is repeated driving one swarm at a time and reports the process instead. Memory held for attempts that never established has no counter today, so the run states what stands in for it: the process's resident memory with the flood on and off, read against the 100 MiB one endpoint may hold in buffered Initial data. The run also needs the counters the Goal item **How incoming attempts ended is visible on a running node** asks for, and no counter does that today: they have to distinguish attempts that became established connections from attempts that ended without one, and the flood's attempts from the committee's, which on this run the ten honest addresses separate. Attempts the listener disposes of before the node is called appear in neither count, since the node is never told of them; they are counted only in the per-endpoint handshake statistics `libp2p-quic` does not reach (see Background), so a column for them depends on a modified crate ({{patched-transport-crate-upkeep}}). Degradation inside that sweep makes the cost of an unvalidated attempt the binding constraint; degradation only above it points after `accept()` ({{pending-inbound-unbounded}}); none at any rate reached means this is not worth acting on. {{accepts-unbounded-per-poll}}, {{endpoint-driver-contention}} and {{single-inbound-socket}} want columns from the same run.

**Cost of an added round trip on a long path.** Never measured. A round trip required before the handshake adds exactly one network round trip to every connection from an address that has not completed one: a protocol property rather than a measured latency, and on a path whose round-trip time is several hundred milliseconds the added delay is that round-trip time by construction. For a single dial, then, the answer is arithmetic; the run exists for the mass reconnect, where a whole committee pays that delay at once, and it prices the added round trip whichever surveyed change introduces one. What it costs this deployment depends on the network between the validators, which is not specified (see Background), so the paths have to be named before the run can be set up. Set-up: on the reference deployment, with both swarms of a node process running, time first dial to established connection over each inter-validator path the maintainers name, once as the listener behaves today and once with one round trip charged before the handshake, either by a change that charges it or by holding the listener's first reply for that path's round-trip time as a stand-in; report the distribution rather than the mean, that path's round-trip time beside it, and which of the two the run used; then repeat both with the whole committee of ten reconnecting at once, which is the condition the honest-peer guard is held to. Direction: an added round trip that stays inside the tolerance **Honest peers unaffected, as the regression guard** is held to, mass reconnect included, leaves a change that charges first contact a round trip inside that guard on the paths measured; one that pushes mass reconnect outside the tolerance rules such a change out on those paths, and the bound **Forged-source flood on production-class hardware** sets has to be reached without charging first contact; and if the two timings differ by less than the run-to-run spread of the reconnect test itself, this measurement decides nothing and the decision rests on the flood run above.

**The three flood runs that exist.** All ran on one desktop-class Intel CPU with libp2p 0.56.0 and `quinn-proto` 0.11.14 against a QUIC server built on the libp2p stack, not this node, with connection identifiers forged rather than source addresses. None is reproduced on current versions, and they do not agree. Across a container bridge the flood was well-formed Initials, every one of which becomes a handshake. An established connection began to degrade between 5,000 and 10,000 forged connection attempts per second, its 256-byte echo tail latency rising from about 2.4 ms to about 24 ms while every request was still answered. At 100,000 forged connection attempts per second and above a legitimate peer could not establish any connection to the victim at all, its dial timing out after 10 s, putting collapse between 75,000 and 100,000. That server had a 212 KB receive buffer and no address validation. On loopback, in one process on `libp2p-quic` 0.13.0, the flood was malformed packets instead. Up to 100,000 of them per second, about 0.98 Gbit/s, left an established QUIC connection on the same listener unaffected, its 256-byte echo tail latency staying under 0.6 ms with no timeouts. At 150,000 per second its tail rose to between 10 and 42 ms and the kernel began dropping datagrams on the shared socket. At 175,000 per second and above, about 1.72 Gbit/s, that endpoint collapsed: most requests on the established connection timed out for the rest of the run (19 of 20 at 200,000 per second, 11 of 20 at 300,000), the server's listener-error rate fell from tens of thousands per second to a few hundred, and the kernel dropped more than sixteen million datagrams on the shared socket — the 175,000 run was killed by its own harness timeout before printing, and the collapse mechanism was inferred rather than profiled. Only about a quarter of those packets reached the point of allocating connection state, the rest discarded at an earlier check, so that flood was cheaper per packet than one of well-formed attempts. For this issue that is the limit on what it shows: a flood in which every attempt is a well-formed Initial reaches that point every time, and its collapse threshold is plausibly lower. A third run, on one endpoint whose QUIC library was modified for it, answered every attempt from an unvalidated source with a sealed token instead of a handshake, which takes the handshake out of what an unvalidated attempt costs. What it measured is where collapse sat with that cost and where it sat without: with a handshake paid for every unvalidated attempt the collapse band was between 75,000 and 100,000 forged attempts per second, and with a token answering them instead no collapse appeared up to 300,000, the highest rate that run reached, where requests on the established connection were answered at a tail of about 80–95 ms; kernel receive-buffer drops stayed in the millions either way. Its forged identifiers came from one attacker address, so it shows a sender that never answers the token, not one that can. It bears on which cost bounds the collapse point; no other approach above has been measured in either harness.

**What one inbound handshake costs the server.** A full inbound QUIC+TLS handshake from an unknown peer cost the server 285.8 µs of CPU at the median and 319 µs at the 99th percentile, measured by an in-process benchmark that drove the real libp2p TLS client and server configurations on one desktop-class Intel CPU with `libp2p-tls` 0.6.2 and `rustls` 0.23.37 on the ring crypto provider; the absolute microseconds run high because CPU frequency could not be pinned, and this is not reproduced on current versions. It is the whole handshake rather than the part before the node's first hook, and it ran with no socket, no kernel path and nothing contending, so it prices the work one attempt costs and not the rate at which attempts arrive. What an attempt holds in memory has only been printed, never measured under load: the QUIC library's connection struct measured 6,016 bytes on x86_64, printed from a compiled program against `quinn-proto` 0.11.14, a struct size only, excluding the TLS handshake state, the connection-identifier index entry and the per-connection task a live connection also holds, and not reproduced on current versions.

**No flood figure here comes from a real network interface.** No measurement exists on a real network interface with receive offload, or behind a provider edge that caps the flood's bandwidth; the harnesses above are emulated media on one host. The absolute packet rate on them is a property of the medium and the CPU rather than of a production node, so what transfers is the shape rather than the threshold. The proposed run sweeps across those rates for that reason: they set where to look, not what to expect.

## Open questions

- **What is the network between validators: link speed, and round-trip times between the places they run?** The reference deployment fixes the hosts and the committee but not the network between them, so the reconnect timings the honest-peer guard is held to have no paths to run over, and **Cost of an added round trip on a long path** cannot be set up at all: its whole result is those paths' round-trip times. The maintainers naming the paths is what unblocks both.
- **What sits between the public internet and a validator's UDP socket, and what does it drop?** The surveyed entry on filtering at the host firewall or the provider edge runs into not knowing what an edge strips, and the same answer decides what interface **Forged-source flood on production-class hardware** is driven over and what stands in front of it. The answer binds the siblings that share that run as well; Related names them. It takes the maintainers stating the hosting arrangement and the host firewall rules.
- **Would `libp2p/rust-libp2p` take a decision point ahead of `accept()`?** Nothing of the kind is open upstream and how such a change would be received is untested, so the surveyed entry on upstreaming one carries neither a cost nor a timeline. Asking upstream settles it.
