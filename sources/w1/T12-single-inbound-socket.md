## Problem

Each libp2p swarm listens on one UDP socket, bound by `libp2p-quic` with no options but `set_only_v6` on IPv6 (`libp2p-quic-0.14.0/src/transport.rs:183-196`):

```rust
        if socket_addr.is_ipv6() {
            socket.set_only_v6(true)?;
        }

        socket.bind(&socket_addr.into())?;
```

It feeds one quinn endpoint (`:220-231`) with one live socket (`quinn-0.11.9/src/endpoint.rs:468-469`) drained by the one task spawned per endpoint (`:149-157`): the endpoint driver, the switch point between that socket and the endpoint routing datagrams to their connections (`:349-355`). Dials reuse it by default (`transport.rs:272-281`; `libp2p-swarm-0.48.0/src/dial_opts.rs:96`).

That queue holds Initials (a connection attempt's first packet, at least 1,200 bytes, RFC 9000 section 14.1), packets on established consensus connections and replies to the node's own dials. Nothing sorts them earlier: a packet is matched by Destination Connection ID (RFC 9000 section 5.2) in user space, once queued, so a full queue drops whatever arrives next, honest consensus traffic included. Any decision taken after a packet is read leaves this socket's load unchanged: no node code runs before that read, which the one draining task performs after taking the endpoint's shared state (`quinn-0.11.9/src/endpoint.rs:367`), so the packet has crossed the queue and the reader by the time anything can decide about it. What an attempt costs past that read is {{quic-initial-unvalidated-cost}}'s.

The queue's depth is the receive buffer, at the operating system's default. `quinn-udp` exposes a setter nothing above it calls (`quinn-udp-0.5.14/src/unix.rs:263`), `libp2p_quic::Config` has no field for it (`config.rs:30-74`), and no `sysctl` or receive-buffer guidance ships in `etc/` or `docs/`: the size moves on the host, not from this repository.

Whether any of this limits a node under flood is unestablished: the two flood measurements below used emulated media and disagree.

## Goal

An investigation. The maintainers set any bound from the numbers; it closes when the measurements below are run and the decisions posted here.

- **Does one UDP socket per swarm limit a node under flood, and at which layer, the receive queue or the endpoint driver draining it?** *Evidence:* **the flood on production hardware** and **the buffer sweep**, reporting kernel drops, driver busy time and connection latency together. *Leads where:* drops rising while the driver has idle time points at the queue, whose depth decision two is about; the driver busy while drops stay near resting points at the reader, which is {{endpoint-driver-contention}}'s; neither rising while the connection degrades anyway leaves this socket unimplicated at either layer and the question with {{quic-initial-unvalidated-cost}} and {{accepts-unbounded-per-poll}}; and neither rising while the connection does not degrade at all, at any rate the link delivers, answers the question as no.
- **Which layer sets the depth of this socket's receive queue, the host or this repository?** *Evidence:* **the buffer sweep** with **the honest path**, since that depth also sets how much honest traffic the socket holds while the reader is busy. *Leads where:* if the depth that does best under flood also holds on the honest path and no host setting reaches it, the layer is this repository; if a host setting reaches it, the layer is the host and what is missing here is documentation; if no depth beats the one the reference hosts run today, neither layer has anything to set.
- **Honest peers are no worse off, whichever way the answer goes.** With all nine remote committee members reconnecting at once on each swarm of the reference deployment (see Background), time from first dial to established connection, small-message tail latency and bulk throughput stay within the readings that **the honest path**'s first run takes at the depth the reference hosts run today with no flood running, by whatever margin the maintainers set from those readings. *Evidence:* **the honest path**, whose first run sets those readings, since no honest-peak figure exists today. *Leads where:* a change that wins under flood and loses here is not an answer on its own, and it goes back to the maintainers with both readings.
- **Non-goals.** Changing what an established peer may do. Choosing an approach: this produces evidence, not a change.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

The node's one transport construction site sets six values on this endpoint (`crates/network-libp2p/src/consensus.rs:563-582`): the handshake and idle timeouts, the keep-alive interval, the concurrent stream limit, and the per-stream and per-connection data limits. None of them is about the socket.

### Approaches surveyed so far

Any of these that changes the transport's socket handling would ship as a modified crate, with the upkeep {{patched-transport-crate-upkeep}} describes.

A separate port for committee traffic. In the node this is a second listener: the network's listen command takes one multiaddr and hands it to `Swarm::listen_on` (`crates/network-libp2p/src/consensus.rs:862-863`), each swarm is started on exactly one address today (`crates/node/src/manager/node.rs:912`, `:949`), and each such call builds its own socket and its own endpoint (see Problem), so committee traffic would arrive on a socket of its own and committee members would have to learn that port; outside the node it is a firewall rule on the same two ports. Both forms sort by address and port before any packet is read, and the threat model above assumes the attacker knows every validator's IP address and port, so a flood reaches both ports; the sorting holds only where the committee port is unreachable from outside, and the acceptance rules require a defence to hold when the host firewall is absent or wrong. The addresses it sorts by are a committee list, which the node replaces from authoritative state at every epoch (`crates/network-libp2p/src/consensus.rs:1084-1095`), and those same rules require failing open when such an input is stale or missing.

Keep one socket and make its receive buffer size settable. The setter is exposed no higher than `quinn-udp` (see Problem), and the socket it would be set on is built by the transport itself, inside `listen_on` (`transport.rs:228`, calling `create_socket` at `:183`), which accepts no socket from its caller, so the size can only be set where the crate builds it. The measured evidence runs both ways (see Measurements).

Operating-system tuning alone: the receive-buffer default, receive-side scaling, busy polling. None of the three is set or documented in this repository (see Problem), so whether a node runs with any of them is a property of each deployment, and for the first of the three the node cannot tell what it got: the getter that would read back the size the host actually gave the socket (`quinn-udp-0.5.14/src/unix.rs:275`) is no more called than the setter.

Separate sockets for listening and dialling. The crate dials from the listening socket by default (see Problem) and the hole-punch path clones it (`transport.rs:319`, `:324`). What separating them does to the address a peer observes is untested; the advertised address is configured, not observed (`consensus.rs:585`).

Several inbound sockets on one port with kernel steering (`SO_REUSEPORT`). Each is its own quinn endpoint with its own socket (`endpoint.rs:468-469`) and its own connection table (`:473`; `quinn-proto-0.11.18/src/endpoint.rs:47-48`), one per listener as the Problem describes, and `quinn-rs/quinn#1576` states that key `quinn_proto::Endpoint` methods take `&mut self` and must change first. That issue also describes the kernel spreading the packets that arrive on one port across those sockets by a 4-tuple hash, which the flood's sender picks, and connections moving between sockets when a peer migrates; a peer whose address changes mid-connection would land elsewhere, such datagrams being dropped today anyway with migration disabled (`config.rs:162`; `quinn-proto-0.11.18/src/connection/mod.rs:1131-1136`).

## Implementation details to pay close attention to

If the receive buffer is treated as a one-way improvement, the measurements below contradict that. If a requested size is taken for the effective one, the two differ: the kernel can clamp a request to the host maximum and double what it grants.

If per-source steering across sockets is counted on, the attacker picks the addresses and ports the kernel hashes. If inbound and outbound were separated, the node's own dial replies leave the listening socket, and the hole-punch path that clones it moves too.

If only one swarm is measured the figure understates a node: each is a separate target whose driver competes for the same cores, and on the reference deployment there are two of them in one process, so one flood arrives at two UDP sockets and two kernel receive queues on the same host (derived, not measured: one socket and one receive queue per swarm, times the two swarms that deployment runs). Starving one is not confined to it: a worker lane that cannot reach peers terminates the process today (#1398). If a change is carried in a per-socket setting, the reference deployment applies it once per swarm; if it is carried in a committee list, an epoch committee change replaces that list under it (see Approaches); and whichever it is, the test lane it would need does not exist ({{quic-listener-interop-tests}}).

## Measurements that would affect the decision

Every figure below is from an emulated medium (a container bridge and loopback, not a network interface) on one desktop-class host, against a QUIC echo server, not this node, with one QUIC endpoint under flood where a node runs one per swarm, and with libp2p 0.56.0 and `quinn-proto` 0.11.14; none is reproduced on current versions. `main` resolves `quinn-proto` 0.11.18, which since 0.11.15 discards a saturating Initial before deriving its keys (`quinn-proto-0.11.18/src/endpoint.rs:455-461`, keys at `:463`) where 0.11.14 derived them first, so the per-packet cost at saturation is not the one these runs paid. Both forged connection identifiers, not source addresses, and neither reported kernel drops and driver busy time together. Collapse below is where a legitimate peer could no longer be served, whether its requests went unanswered or it could not connect at all.

They measured different victims and are not reconciled. On the bridge an established connection began to degrade between 5,000 and 10,000 well-formed attempts per second, its 256-byte echo tail latency rising from about 2.4 ms to about 24 ms with every request still answered; from 25,000 to 75,000 it stayed up and answered every request, that tail pinned near 30 ms and its median climbing to about 12 ms; at 100,000 and above a legitimate peer could not connect at all, so collapse lies between 75,000 and 100,000, while total server CPU never passed about 1.5 of its 3 cores. On loopback, against a malformed flood only a quarter of which reached connection state, a connection held to 100,000 and collapsed at 175,000. Bridge kernel receive-buffer drops rose from about 30 at rest to 2.7 million at 75,000 per second, indiscriminately: the peer's packets go with the flood's, both on the same socket.

Both floods' server accepted every attempt, as `libp2p-quic` does: it accepts every incoming attempt unconditionally (`transport.rs:595`). One modified run bears on this socket only through where the collapse sat, and it measures an approach no entry above surveys: when every attempt from an address that had not completed a round trip was answered with a sealed token instead of a handshake (an address-validation token the server issues and the sender has to return before a handshake starts, RFC 9000 section 8.1.2), collapse moved from between 75,000 and 100,000 per second to beyond 300,000, at a 99th-percentile tail of 80-95 ms there, while kernel receive-buffer drops stayed in the millions either way, so the collapse point moved while what the queue shed did not, which puts that run's effect on the cost each attempt carries past the read, and that cost is {{quic-initial-unvalidated-cost}}'s. Source-address forging could not be emulated there, so every packet left one attacker address: it shows a sender that never answers the token, not one that can, unlike the threat model's rented hosts. Of the approaches surveyed above, only the receive buffer has been measured in either harness, in the paragraph below, and there only as the depth it gives the queue rather than as the layer that sets it: not a separate port for committee traffic, not several inbound sockets on one port, and not a separate dialling socket.

The buffer points both ways there. The server ran on the container's 212 KB default because the QUIC library does not raise the socket receive buffer and the host maximum could not be changed from inside the container. Raising it to about 8 MB cut the established connection's tail latency at 10,000 and 25,000 per second from about 25-30 ms to 8-9 ms, with kernel drops falling from hundreds of thousands to near zero, but moved collapse down to about 50,000, which the smaller buffer had survived. That a small buffer sheds most of the flood in the kernel while a larger one feeds more to the single reader is a hypothesis, never profiled.

**The flood on production hardware.** One run against both swarms of one node process at once, on the reference deployment (see Background), reporting per swarm the kernel's receive-buffer drops and the endpoint driver's busy time and, for a legitimate peer that is not part of the flood, time to established connection, small-message tail latency and bulk throughput. That peer carries the bridge harness's workload, so the readings compare with it: a 256-byte request on its own stream every 50 ms, with a 1 MiB bulk stream running in the background. The drops have to separate datagrams the kernel discarded for a full queue from datagrams it delivered, per swarm's socket; they are a host counter rather than a node one, the kernel's own receive-buffer drop counters for that socket, which is where the bridge run read them. Busy time has to separate the time the driver spends running from the time it spends idle, per swarm; nothing in node-owned code observes that today, so obtaining it depends on a modified `quinn`, with the upkeep {{patched-transport-crate-upkeep}} describes, if it is obtained that way. Rates sweep from below the bridge harness's degradation onset past its collapse point and beyond 300,000 per second, with well-formed and malformed attempts. At the 1,200-byte minimum an Initial carries (RFC 9000 section 14.1), a rate of R well-formed attempts per second is R × 9,600 bit/s of UDP payload, a floor because headers are on top of it: about 0.7 Gbit/s at 75,000 per second, about 1.0 Gbit/s at 100,000 and about 2.9 Gbit/s at 300,000 (derived, not measured). The in-scope top of the sweep is therefore wherever that byte rate reaches the link the maintainers supply, since the acceptance rules leave a flood that saturates the link out of scope; malformed attempts, which need not carry that minimum, reach a given rate on fewer bits. Because the reference deployment already runs two sockets on one host, the per-swarm columns are also what this run shows for the layout entries: what a second socket on the same host takes and relieves under one flood that reaches both of them. {{quic-initial-unvalidated-cost}}, {{accepts-unbounded-per-poll}} and {{endpoint-driver-contention}} need columns from this run, so run it once; the network between validators, and with it the interface the flood arrives on and the top of the sweep, is the one input the maintainers still supply.

**The buffer sweep.** That run repeated across requested receive buffer sizes, doubling at each step, from the size the reference hosts give the socket today (nothing records it, so it is read first; see Open questions) past the region the bridge harness reached at about 8 MB. Each size is requested through the host's own setting for it, which is the same parameter whether the operating system or this repository would be the one to set it, and the effective size is read back at each step, because the kernel can clamp a request and double what it grants (see above); nothing in this stack reads it back (see Approaches), so that readback carries the same modified-crate dependency as the busy-time column above. Drops alone cannot tell an undersized buffer from a stalled drain; this can, since raising the size clears drops either way but only an undersized buffer survives to a higher rate. For the layout entries the sweep says whether one queue's depth is what binds: a size that clears the drops without moving the collapse point says it is not, which leaves the reader and the layout as what is still to be separated.

**The honest path.** The same three connection readings with no flood, on the same deployment, at each size in the sweep, the peer carrying the same workload as above, for a mass reconnect of all nine remote committee members on both swarms and for a path that loses packets, that second case because the network between validators has not been specified and what the buffer does to honest traffic depends on it. No figure exists for any of these readings today. For the layout entries this run is the honest-side bar: a mass reconnect puts the node's own dials and the peers' attempts on the same socket at once, which is the traffic a separate dialling socket would split, and the readings taken here are what any change to this socket, layout or depth, is read against.

## Open questions

- **What is the honest peak this socket has to carry, and what completion time counts as no worse off?** The Goal's honest-peer item is written against readings that do not exist: the committee size is known, so a mass reconnect on the reference deployment is nine remote members arriving at each swarm, but nothing records how fast they arrive or how long the three readings take today, in this harness or any other. The first run of **the honest path** sets them; what counts as no worse off afterwards is a decision for the maintainers.
- **Does the kernel on the reference hosts spread packets arriving on one port across several sockets the way the upstream issue describes?** The several-sockets entry rests on `quinn-rs/quinn#1576` for the 4-tuple hash and for connections following a peer that migrates, and on nothing else: that behaviour has not been checked against the operating system's own documentation for the option, nor observed on a host here. It matters because the addresses and ports being hashed are the attacker's to pick, which is the constraint that entry runs into. The platform's documentation for the option, or a run on the reference deployment's hosts, would settle it.
- **What run would put evidence behind a changed socket layout?** The three measurements read today's layout and say what that shows for the entries that would change it (see Measurements), but none of them, and no run in either harness, has a separate committee port, several inbound sockets on one port or a separate dialling socket behind it. What such a run would need, and whether it belongs to this issue or to one of its own, is a decision for the maintainers.
- **Which way does a larger receive buffer move honest throughput?** Decision two turns on a trade-off whose measured evidence sits entirely on the flood side: the tail latency and the collapse point were both read with a flood running, and no entry in either harness records what a buffer size does to throughput on a connection that is not under flood. The bulk-throughput reading of **the honest path** would supply the missing side.
- **What receive buffer do the reference hosts actually give the socket?** The size moves on the host, this repository ships no guidance for it, and the only figure anywhere is the 212 KB the container harness ran on, which was that container's own default; whether the reference hosts run at theirs or at a value tuned away from it is not recorded anywhere. Both decisions are read against whatever it turns out to be, and **the buffer sweep** starts from it. Either the effective size that sweep reads back, or the maintainers reading the setting on the reference hosts, would establish it.
- **What is the network between validators?** Link speed and round-trip times are the one reference-deployment input still unspecified, and two measurements need it: **the flood on production hardware** sweeps rates an interface has to deliver, and **the honest path**'s lossy case has no loss or delay to run at. The link speed also sets where that sweep stops being in scope, since well-formed attempts at a given rate imply a byte rate (see Measurements) and the acceptance rules leave a flood that saturates the link to the hosting provider. The question is shared with the siblings that need the same run, {{quic-initial-unvalidated-cost}}, {{accepts-unbounded-per-poll}} and {{endpoint-driver-contention}}. The maintainers supply it.
