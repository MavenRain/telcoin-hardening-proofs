## Problem

An **Initial**, the first packet of a QUIC connection attempt, carries the TLS ClientHello. `quinn` gives each endpoint one **endpoint driver** — the task that reads the UDP socket and routes datagrams to connections — and one `Mutex<State>` it shares with the accept path. The driver holds that lock for a whole poll (`quinn-0.11.9/src/endpoint.rs:367`), calling `Endpoint::handle` under it per datagram (`:798`); for an Initial that means deriving Initial keys (`quinn-proto-0.11.18/src/endpoint.rs:463`), stripping header protection (`:487`), buffering the attempt (`:521-525`). Established connections get inbound data only through that call, routed by connection id to their own tasks (`:244-247`; `quinn-0.11.9/src/endpoint.rs:815-823`), so none progresses while it is held. Each of this node's endpoints belongs to a `ConsensusNetwork`, the primary's or a worker's (`crates/node/src/manager/node.rs:1244`, `:1282`), so what waits behind the lock is the node's own consensus traffic to peers it is already connected to.

Accepting an attempt takes the same lock again, on the **swarm task** — the tokio task polling one `Swarm` and every behaviour on it. `libp2p-quic`'s listener calls `incoming.accept()` (`libp2p-quic-0.14.0/src/transport.rs:595`) inside the swarm poll (`libp2p-swarm-0.48.0/src/lib.rs:1250`, driven at `crates/network-libp2p/src/consensus.rs:775`), reaching `EndpointInner::accept`, which opens `let mut state = self.state.lock().unwrap();` (`quinn-0.11.9/src/endpoint.rs:419`).

All of `Endpoint::accept` runs in that critical section, including the server's first flight, every TLS message it sends in reply to a ClientHello: the first packet's CRYPTO frames pass from `handle_first_packet` (`quinn-proto-0.11.18/src/endpoint.rs:665`) through `read_handshake` (`quinn-proto-0.11.18/src/connection/mod.rs:2141`) into rustls (`rustls-0.23.37/src/quic.rs:421-422`), which selects the key-exchange group (`rustls-0.23.37/src/server/tls13.rs:204-208`), completes key agreement (`:502`, call site `:342`) and signs `CertificateVerify` (`:787`, call site `:394`). None of it is deferred: the `write_handshake` hop that follows in the same call (`quinn-proto-0.11.18/src/connection/mod.rs:2153`) only drains handshake bytes rustls has already queued (`rustls-0.23.37/src/quic.rs:490-497`). All of that is the server's side of the flight, and all of it runs under the endpoint lock, on the swarm task.

Nothing bounds how long it is held. The driver's poll budgets its own work, 50 µs of receive time spent across whole batches (`quinn-0.11.9/src/lib.rs:136`, applied at `quinn-0.11.9/src/endpoint.rs:494-507`) and 160 connection events drained per poll (`quinn-0.11.9/src/lib.rs:128`, applied at `:518`), but neither budget covers the time a single `Endpoint::handle` call takes under the lock. Hold time per Initial has never been measured, so the effect's size is unknown.

## Goal

Decide whether contention on the quinn endpoint driver task and endpoint mutex binds this node.

- **The decision, and where each result leads.** *Observable:* mutex hold time per Initial and per accept, and added latency on an established connection sharing that endpoint, against attempt rate. *Baseline:* "Hold time against attempt rate, on one endpoint" below records it, over the rate range that measurement's sweep covers. What counts as added latency that matters to consensus traffic is a property of the node's consensus timing and is settled there, not from this run (see Open questions); the run's figures are judged against it. If hold time times attempt rate accounts for that latency while receive-buffer drops and swarm-task poll latency stay flat, contention binds and every entry under Approaches bears on it. If drops or scheduling move first it does not, and the work belongs to {{single-inbound-socket}} and {{accepts-unbounded-per-poll}}. If latency never moves, the question closes.
- **Honest load measured too, not only an adversarial rate.** The run also drives an **honest mass reconnect**, the burst of legitimate handshakes when many peers reconnect at once: a restart, a partition healing, an epoch committee change. That burst is a shape, not a point on the adversarial rate axis and not swept: on the reference deployment (see Background) it is the nine remote members of a ten-validator committee dialling one swarm together from a standing start, plus the non-committee peers the node carries, whose number is an open question below; it is driven once per trial and the trial repeated, so the result is a distribution rather than one sample. *Observable:* per dial in the burst, the time from that dialer's first packet to its connection being established, read until the last dial of the burst is established or has timed out, and how many of the burst's handshakes were refused. *Baseline:* "Hold time against attempt rate, on one endpoint" records both figures for that burst, and the maintainers set the honest-peer bound reading them: how much a change may add to dial-to-established, and how many refusals of an honest handshake, if any, are tolerable. The run's figures are the baseline that bound is read against, not the bound itself.
- **Non-goals.** Choosing any remedy. Setting any limit. Changing what an established peer may do.
- **Closed by** the figures of "A flood on the reference host, against every swarm at once", its two-swarm leg included, read together with the hold times "Hold time against attempt rate, on one endpoint" records in both of its legs, all recorded against the crate versions they ran on, and a decision naming the branch taken.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

Upstream reports the same hold, the endpoint lock kept across TLS session setup and first-packet handling, twice. `quinn-rs/quinn#2782`, an open pull request whose two predecessors `#2771` and `#2775` merged, says it "stalls the endpoint driver whenever it encounters a new Initial" and cuts throughput for established traffic; `quinn-rs/quinn#2795`, a pull request closed unmerged as covered by `#2782`, reported the same stall independently. `quinn` 0.11.9, the version `Cargo.lock` resolves, carries neither.

### Approaches surveyed so far

Bound the work reaching the endpoint, leaving the structure alone. The driver still calls `Endpoint::handle` per datagram, and quinn's pre-accept bound `max_incoming` — attempts received but not yet accepted or disposed of — has no field in `libp2p-quic`'s configuration ({{quic-initial-unvalidated-cost}}).

Drive handshakes and established traffic from separate endpoints on one swarm. `libp2p-quic` creates one socket (`libp2p-quic-0.14.0/src/transport.rs:228`) and one endpoint (`:231`) per listener, so datagrams would need routing by connection id across sockets ({{single-inbound-socket}}); `quinn-rs/quinn#1576`, an open issue, describes the `SO_REUSEPORT` form and the interior mutability needed.

Move the accept call off the swarm task onto one of its own, so that the accept-side hold, one of the two this issue measures, falls on that task rather than on the one polling the swarm. `EndpointInner::accept` still takes the mutex the driver takes, so the critical section is unchanged, and the type calling `incoming.accept()` is private to the crate (`libp2p-quic-0.14.0/src/transport.rs:419`).

Take the upstream change. `quinn-rs/quinn#2782`, open, moves TLS and first-packet handling out of the critical section, which the pull request says leaves the caller to bound handshake concurrency, since it is the lock that serializes accepts today; `libp2p-quic` exposes no such bound (`max_incoming`, above).

None of the four arrives from a released dependency today; each would be delivered as a modified transport crate, and {{patched-transport-crate-upkeep}} is the upkeep that dependency carries.

## Implementation details to pay close attention to

If hold time is measured at rest it misses what matters: contention is attempt rate times hold time. A rate axis covering one regime only bounds nothing about the other: an adversarial rate says nothing about an honest mass reconnect, an honest rate nothing about what a real-address botnet sustains ({{validated-address-handshake-rate}}).

If the flood and the established peer share one host or bridge, the socket receive buffer overflows before the lock does and the run measures the buffer instead.

If hold time is taken on one endpoint it under-reports a node: the reference deployment runs two swarms in one process, so two endpoints, each with its own driver task (`quinn-0.11.9/src/endpoint.rs:149-150`) and its own state mutex, and two swarm tasks (`crates/node/src/manager/node.rs:1256`, `:1296`), and every per-swarm cost counts twice. If the second endpoint is idle while the first is timed, the figure holds only for that case: the two mutexes are separate, so neither endpoint waits on the other's lock, but all four tasks run on one multi-threaded tokio runtime whose worker threads default to the host's CPU count (`crates/telcoin-network-cli/src/cli.rs:161-165`; `tokio-1.53.1/src/runtime/builder.rs:2008`, `tokio-1.53.1/src/loom/std/mod.rs:85-99`), which on the reference deployment's 8 CPUs is eight worker threads (derived from the supplied hardware, not measured), shared with every other task the node runs.

If a future `quinn` and `quinn-proto` resolve with `quinn-rs/quinn#2782` in them, the critical section changes underneath whatever is decided here, and a figure taken now describes the older one.

## Measurements that would affect the decision

**Hold time against attempt rate, on one endpoint.** The single-endpoint leg, which sets the baselines the Goal reads and does not on its own stand for a node running two. Wanted at every point of both legs, and what each has to distinguish: mutex hold time per Initial on the driver and per accept on the swarm task, which separate time the lock is held from time spent waiting for it; added latency on an established connection carrying the node's own point-to-point request-response protocol (`req_res`, `crates/network-libp2p/src/consensus.rs:452-455`), at a message size and request rate held constant across the sweep so that a latency change belongs to the sweep and not to the workload; kernel receive-buffer drops, which separate a latency rise caused by the lock from one caused by datagrams the kernel discarded before `quinn` read them; swarm-task poll latency, which separates the swarm task being slow to return to its own work from the endpoint being slow to hand it any. Of the four, only poll latency can be read from node-owned code today: the swarm's event arm and the loop around it are the node's (`crates/network-libp2p/src/consensus.rs:775`, with the loop's gauges updated once per iteration at `:794`). Neither hold time is exported by anything the node depends on: `EndpointStats` counts handshakes accepted, refused and ignored, and no durations (`quinn-0.11.9/src/endpoint.rs:91`, `:338-348`), and `libp2p-quic` keeps its listener type private (`libp2p-quic-0.14.0/src/transport.rs:419`), so if the two are to be read at all the run depends on a locally modified `quinn`, and on the upkeep {{patched-transport-crate-upkeep}} describes. The drop count is not the node's to read either: the socket belongs to `libp2p-quic` (`libp2p-quic-0.14.0/src/transport.rs:228`), and {{single-inbound-socket}} owns the question that socket raises. Sweep the adversarial axis from below the container-bridge harness's degradation onset to above its collapse point, both of them given under "What the two flood harnesses already bound" below. The link bounds the top of that sweep as well: a client must expand the payload of the datagram carrying an Initial to at least 1,200 bytes (RFC 9000 section 14.1), and 1,200 bytes is 9,600 bits, so R attempts per second is at least R × 9,600 bit/s of payload on the wire; the sweep stops below the rate at which that reaches the reference deployment's link, which has not been specified (see Open questions), because above that rate the run measures a saturated link, and the acceptance rules put a flood that saturates the link out of scope. The honest reconnect burst is the other leg rather than a point on that sweep: it is driven in the shape the Goal's second item describes, once with the endpoint otherwise at rest and once while the sweep runs, so dial-to-established is read both with contention present and without it. Core count and clock change the answer, so a decision taken on a development host is provisional until the figures are retaken on the reference host (see Background).

**A flood on the reference host, against every swarm at once.** Not run. Wanted: established-connection latency against attempt rate with one swarm flooded, then the same with both of the host's swarms flooded together, and the driver and accept hold times of each endpoint read alongside. If flooding both swarms degrades established latency further than flooding one, the two-swarm figures are what the decision is taken on and a single-endpoint figure under-reports the node; if the two are indistinguishable, this run is what establishes that, and the single-endpoint figures then stand for the node; if established latency moves at neither the adversarial rates nor the honest burst, the question closes for this hardware class. {{quic-initial-unvalidated-cost}}, {{accepts-unbounded-per-poll}} and {{single-inbound-socket}} need the same run: one run, carrying all four sets of columns.

**What the two flood harnesses already bound.** Both drove an echo server on the same libp2p stack, not this node, and disagree: onset an order of magnitude apart, collapse a factor of about two. Across a container bridge, the server pinned to 3 cores of an 8-core desktop host, an established connection degraded between 5,000 and 10,000 forged connection attempts per second — 256-byte echo tail latency rising from about 2.4 ms to about 24 ms, every request still answered — while at 100,000 and above a legitimate peer could not connect at all, its dial timing out after 10 s, putting collapse between 75,000 and 100,000. At every rate, collapse included, server CPU stayed below about 1.5 of those 3 cores, so the host was not CPU-saturated when it stopped accepting connections: consistent with a serialisation point, a lock or a single task, and equally with a socket receive buffer overflowing. On loopback an established connection was unaffected up to 100,000 malformed attempts per second; at 175,000 and above the endpoint collapsed and most of its requests timed out for the rest of the run (19 of 20 at 200,000 per second, 11 of 20 at 300,000). Both ran on one desktop-class Intel CPU with libp2p 0.56.0 and `quinn-proto` 0.11.14, not reproduced on current versions: the bridge forged connection identifiers rather than source addresses, on a 212 KB receive buffer with no address validation; on loopback only about a quarter of the packets reached connection-state allocation, and collapse was inferred rather than profiled.

Neither separates driver contention from socket-buffer overflow or swarm-task starvation, though one modified bridge run partly does, reported under {{quic-initial-unvalidated-cost}}; no approach above is measured in either. No flood measurement exists on a real network interface with receive offload, or behind a provider edge that caps the flood's bandwidth: both media are emulated, so what transfers from them is the shape rather than the rate. Both predate the `quinn-proto` change, landed in 0.11.15, that ignores an Initial at `max_incoming` saturation before deriving Initial keys (`quinn-proto-0.11.18/src/endpoint.rs:455-461`, keys `:463`).

## Open questions

- **How long is the endpoint lock actually held, per Initial and per accept?** The Problem admits it has never been measured, and every branch of the decision compares hold time times attempt rate against added latency on established traffic, so nothing here can be decided without the figure. "Hold time against attempt rate, on one endpoint" is written to produce it.
- **How much added latency on established consensus traffic is too much?** "The decision, and where each result leads" routes on whether hold time times attempt rate accounts for the added latency that matters to consensus traffic, and the node's network configuration states no such figure: its durations are coarse recovery bounds, such as the 30-second consensus round timeout declared at `crates/config/src/network.rs:316` (default at `:358`), described there as a safety measure for a node that has not received enough parents for a round in time. What settles it is a decision by the maintainers about consensus timing, taken against the pacing those durations describe; the run's figures are then judged against that decision.
- **How many peers beyond the committee does a node carry?** The reference deployment fixes the committee at ten, so nine remote members dial each swarm, but it does not say how many non-committee peers connect, and the honest reconnect burst is the sum of the two. Today's configuration bounds only part of that sum: `max_peers()` works out to 39 on defaults (`crates/config/src/network.rs:489-491`), and the peers the node treats as important, validators among them, are exempt from it (`crates/network-libp2p/src/peers/manager.rs:894-897`). The maintainers supply the expected population, or the run states which population it drove.
- **What is the network between validators?** Link speed and round-trip times have not been specified (see Background), and the two bear directly: the top of the sweep's rate axis is where minimum-size Initials fill the link, and the dial-to-established figure under "Honest load measured too, not only an adversarial rate" is read against the round-trip times; the medium of a flood run is undecided for the same reason, both existing harnesses having run on emulated media. The maintainers supply it, and {{quic-initial-unvalidated-cost}}, {{accepts-unbounded-per-poll}} and {{single-inbound-socket}} need the same input for the run they share with this one.
- **Will `quinn-rs/quinn#2782` merge, and when?** The hold times "Hold time against attempt rate, on one endpoint" would record are those of the critical section `quinn` 0.11.9 has, and if a released `quinn` and `quinn-proto` carry that change they describe a critical section the node no longer runs, which is the version-drift hazard above. Upstream settles it; nothing in this repository does.
