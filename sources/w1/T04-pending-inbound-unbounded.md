<!-- title: network-libp2p: a swarm holds unboundedly many unfinished inbound handshakes, unattributed to any source -->
<!-- labels: security, enhancement -->

## Problem

An inbound connection is pending between the transport handing it to the swarm and the handshake finishing, when the `PeerId` becomes known. Each holds a QUIC connection object, TLS handshake state, a connection-identifier index entry and a spawned upgrade task (`libp2p-swarm-0.48.0/src/connection/pool.rs:478-494`). Nothing caps, attributes or records them, so a remote starting handshakes it never finishes holds that state on every swarm until a deadline expires it. How much a swarm holds at once is the rate attempts arrive at multiplied by how long each one is held, and the node chooses neither factor: the sender sets the rate, and every attempt is held to the same fixed deadline. That state accumulates inside the process that also runs this node's consensus. Which resource gives out first — memory, spawned tasks, time on the task that polls the swarm — is unmeasured, and the node exports no count that would show it happening.

Addresses here are unvalidated: `libp2p-quic` accepts every incoming attempt unconditionally (`libp2p-quic-0.14.0/src/transport.rs:595`), so nothing has shown the sender can receive packets where it claims (RFC 9000 section 8.1); it may be a forged source that never sees the reply.

Nothing bounds how many exist at once. `crates/network-libp2p/src/consensus.rs:133-138` sets one connection-limits dimension, the per-peer established ceiling of `8` added for #1010 (`consensus.rs:124`), leaving the rest, pending totals included, "intentionally left unbounded" (`consensus.rs:129-131`). Nothing in `crates` or `bin` sets `max_pending_incoming`, and an unset field reads as `u32::MAX` (`libp2p-connection-limits-0.7.0/src/lib.rs:117-118`).

Nothing records how many one source holds. `handle_pending_inbound_connection`, the hook called here, receives two addresses and no peer parameter (`libp2p-swarm-0.48.0/src/lib.rs:955-959`); the connection-limits behaviour discards both (`libp2p-connection-limits-0.7.0/src/lib.rs:235-240`), and the node's own implementation passes the remote address to a ban check, keeping no count (`crates/network-libp2p/src/peers/behavior.rs:77-85`). How limits are keyed is {{validated-address-handshake-rate}}.

The binding deadline is not the one the node configures. The 65 s `handshake_timeout` (`crates/config/src/network.rs:400`, `consensus.rs:566`) is destructured away as `handshake_timeout: _` when the quinn config is built (`libp2p-quic-0.14.0/src/config.rs:139`) and applied instead by wrapping the connection future — one field, inbound (`transport.rs:610`) and outbound (`:308`). The swarm builder then wraps that transport in a 10 s `TransportTimeout`, one value for both directions (`libp2p-0.57.0/src/builder/phase/swarm.rs:5`, `build.rs:28`; `libp2p-core-0.44.0/src/transport/timeout.rs:58-64`); the smaller governs, so the bound on an unfinished inbound connection is 10 s and the configured 65 s has no effect.

Both events reporting an inbound connection's outcome are discarded. A refusal at the pending hook emits `FromSwarm::ListenFailure` and queues `SwarmEvent::IncomingConnectionError`, both `peer_id: None` (`libp2p-swarm-0.48.0/src/lib.rs:964-980`); a failed handshake emits the same pair from `PoolEvent::PendingInboundConnectionError` (`:858-873`) after one `tracing::debug!` line (`:857`). Neither the swarm loop (`consensus.rs:804-855`) nor the peer behaviour (`peers/behavior.rs:136-169`) matches either; both reach catch-alls (`consensus.rs:854`, `behavior.rs:163`), and the metrics (`crates/network-libp2p/src/metrics.rs:24-38`, `:97-117`) have no inbound counterpart to `dial_failures_total`.

## Goal

- **Pending inbound occupancy is bounded.** What a swarm holds between accept and establishment, and the memory behind it, stay under a bound the maintainers set, however fast attempts arrive and however long they are left unfinished. *Observable:* peak pending connections per swarm and resident memory under a driver that starts inbound handshakes without finishing them, which has to be built. *Bound:* none today; set from **Honest reconnect peak** and **Per-pending-connection footprint**.
- **One remote cannot take the whole of pending occupancy from the others.** While one remote opens inbound handshakes it never finishes, as fast as it can, a peer that has none open still reaches established. *Observable:* a test that runs the two side by side and asserts the second connection completes. *Baseline:* nothing today limits or records what a single source holds. Whether this item has to be met for the issue to close depends on how far apart **Honest reconnect peak** and **Per-pending-connection footprint** put honest and hostile occupancy (see Open questions).
- **Failed inbound handshakes are counted, and the two causes distinguishable.** *Observable:* a test asserting a refusal and a handshake failure each increment their own count. *Baseline:* zero.
- **Honest peers unaffected.** *Observable:* a full-committee reconnect on the reference deployment reports dial-to-established time and the number of inbound refusals, which is zero. *Bound:* the tolerance comes from **Honest reconnect peak**, run first on `main` at `9b2a06b7`.
- **Non-goals.** Surviving a link-saturating flood. Changing what an established peer holds, or what an attempt costs before accept. Deciding which identities the node admits.
- The issue closes with the counts landed, the measurements below recorded, a bound on pending occupancy derived from them with its inputs, and the tests above in the suite.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

The pending window closes at `handle_established_inbound_connection` (`libp2p-swarm-0.48.0/src/lib.rs:734-739`), where the ban check and per-peer ceiling apply. What an attempt costs before it opens is {{quic-initial-unvalidated-cost}}; the arrival rate is {{validated-address-handshake-rate}}; what a peer holds afterwards is {{per-peer-ceilings}}. Accounting keyed on an unvalidated address is attacker-controlled: the attacker picks it, and can fill a victim's share with the victim's address.

### Approaches surveyed so far

**Exemption for committee addresses.** Constraint: the sets it would check are keyed by identity, the previous, current and next committees each being a set of `BlsPublicKey` (`crates/network-libp2p/src/peers/all_peers.rs:59`, `:61`, `:65`), while the hook that would apply the exemption receives two addresses and no peer parameter (`libp2p-swarm-0.48.0/src/lib.rs:955-959`), so the match falls back to an address, and addresses here are unvalidated, as above.

**Per-source occupancy accounting.** Constraint: the addresses it would key on are unvalidated, as above; one IPv6 /64 holds 2^64 of them; NAT puts several honest peers behind one; and the hook runs after the transport has accepted (`libp2p-quic-0.14.0/src/transport.rs:595` precedes `TransportEvent::Incoming` at `:609-614`), so what it counts is already allocated.

**Reaction to failed inbound handshakes, by scoring a source.** Constraint: the addresses it would score are unvalidated and both events reporting an inbound failure are discarded, both as above, so there is no record of how often honest inbound handshakes fail.

**Shorter deadline on the inbound side.** Constraint: an inbound-only constructor for the outer timeout exists in the core layer (`libp2p-core-0.44.0/src/transport/timeout.rs:76-82`), while both values in force here are set for both directions at once — `libp2p-quic` carries one `handshake_timeout` field and applies it to both (`libp2p-quic-0.14.0/src/config.rs:33`), and the builder's only override of the outer timeout sets one value for both and is never called here (`libp2p-0.57.0/src/builder/phase/build.rs:21-24`); an inbound-only deadline carried in a modified transport crate would depend on the upkeep {{patched-transport-crate-upkeep}} describes, and how close a shorter one comes to an honest handshake is unmeasured.

**Whole-swarm ceiling on pending inbound connections.** Constraint: the dimension `libp2p-connection-limits` offers has no per-source term, its hook discarding both addresses (`libp2p-connection-limits-0.7.0/src/lib.rs:235-240`), so one count is enforced whoever fills it, and an honest mass reconnect competes for it with everything else.

## Implementation details to pay close attention to

If pending occupancy is released on `FromSwarm::ListenFailure`, then it can release a slot never taken: the swarm emits that event when the pending hook refuses (`libp2p-swarm-0.48.0/src/lib.rs:964-971`), when the handshake fails (`:858-873`) and when the established-inbound hook refuses (`:741-761`), the first two with `peer_id: None` and the third with `peer_id: Some`.

If a bound or an exemption depends on a set that turns over at an epoch boundary, or is derived from steady-state occupancy rather than the honest reconnect peak, then it fails just when a restart, partition heal or epoch change has the whole committee reconnecting; the node tracks previous, current and next committees (`crates/network-libp2p/src/peers/all_peers.rs:59`, `:61`, `:65`), so whether such a check is stale depends on when each set is updated.

If a bound or a count is derived from a host-level budget but enforced per swarm, then each swarm on the host gets the whole of it: one connection-limits behaviour is constructed per swarm (`crates/network-libp2p/src/consensus.rs:205`, reached once per swarm from `:532`), so a host holds as many copies of whatever is accounted as it runs swarms, two on the reference deployment. The same multiplication applies to today's absent bound, unset on both swarms and reading as `u32::MAX` as the Problem says, so each swarm admits pending inbound connections against a ceiling no host could reach. On the reference deployment's two swarms the limits layer therefore imposes no bound at all, and what bounds occupancy is the host's memory rather than the limit; that is derived from the default and the reference deployment, not measured, and what one connection actually costs is **Per-pending-connection footprint**. A maintainer setting any value from those measurements needs the same inputs whatever that value governs: the committee size, ten on the reference deployment; the eight established connections per peer already allowed (`consensus.rs:124`); the size of an honest reconnect burst; the host's memory budget out of those 32 GB; and that swarm count of two.

If the hold time for an unfinished inbound connection is shortened, then an honest handshake that needs longer than the new deadline is dropped before it finishes: how long an honest inbound handshake takes here is the dial-to-established time under **Honest reconnect peak**, which depends on the network between validators and so is not available yet, and a mass reconnect is when the most handshakes are in flight at once.

If inbound admission changes, then a peer on the stock crates of this release or the previous one sees only a closed connection with no reason attached, so an interoperability regression looks like an ordinary handshake failure until those failures are counted ({{quic-listener-interop-tests}}).

## Measurements that would affect the decision

**Honest reconnect peak.** Peak concurrent pending inbound connections per swarm, and dial-to-established time, during a full-committee reconnect on the reference deployment: ten validators on the reference host, both swarms of the one node process read separately, each swarm reconnecting to the nine remote committee members and to whatever non-committee peers it holds. The network between validators is still an input the maintainers supply, and until it is, dial-to-established time from this run stands for the deployment it was run on rather than for production. What the count has to separate is an attempt still pending from one that has reached established, and both hooks that bound the pending window are the node's own (`crates/network-libp2p/src/peers/behavior.rs:77-85` and `:87-108`), so the figure is readable on today's code. If the honest peak sits far below the peak occupancy under sustained unfinished handshakes that **Per-pending-connection footprint** records, occupancy on its own tells honest from hostile; if the two overlap, occupancy on its own cannot, and attribution or hold time has to.

**Per-pending-connection footprint.** All-in memory and task cost of one pending inbound connection on the resolved versions and on the reference host, and the peak occupancy sustained unfinished handshakes reach there. Neither is measured. The occupancy side is counted at the same two node-owned hooks as **Honest reconnect peak**; the memory side is the process's resident memory read against that count, since no node-owned counter reports what one pending connection holds (`crates/network-libp2p/src/metrics.rs:97-117`) and the state the Problem lists sits in the swarm's pool (`libp2p-swarm-0.48.0/src/connection/pool.rs:478-494`), so a per-connection breakdown of it would have to come from a modified crate and would carry the upkeep {{patched-transport-crate-upkeep}} describes. Two earlier flood runs exist, and neither ran against this node: both drove a QUIC server whose transport config mirrors the node's, one across a container bridge between containers, the other on loopback inside one process, both on a single desktop-class Intel CPU and on libp2p 0.56.0 with `quinn-proto` 0.11.14; neither ran against forged source addresses — the bridge run could not emulate them and the loopback run had both ends in one process on `127.0.0.1` — and each flooded one endpoint where a node runs one per swarm. In the bridge run the victim server held at most about 40,000 half-open connections at once (attempts it had accepted whose handshakes never finished), each one a fully allocated connection object, but that ceiling was set by the attacker's fixed pool of connection identifiers, not by any limit in the server, so a flood that kept generating fresh identifiers would accumulate more; memory per connection was not measured in that run. In the loopback run only about a quarter of the malformed connection attempts got far enough for the server to allocate connection state, the rest being discarded at an earlier check, so a flood of well-formed attempts, every one of which would reach that point, is more expensive per packet and its collapse threshold is plausibly lower. Neither run is reproduced on current versions. What the bridge figure bounds, from below, is how far occupancy climbs when nothing in the server stops it, since the attacker's identifier pool and not the server set that ceiling; the loopback fraction is why the two harnesses disagree on what a packet costs; and neither run puts a number on the per-connection memory asked for here. If the footprint is small beside the host's memory budget, occupancy well above the honest reconnect peak still fits on the host and what stays undecided is attribution; if it is large once multiplied by the two swarms of the reference deployment, the reference host's 32 GB is what caps occupancy, and this figure says where that cap falls.

**Honest inbound handshake failure rate.** How often an inbound handshake from an honest peer fails, per swarm per hour, on a devnet of ten honest nodes, the size of the reference deployment, over a window that includes an epoch change and a restart of a committee member. It cannot start until the two inbound-failure events the Problem lists as discarded are counted; both reach catch-alls in the node's own swarm loop and peer behaviour, so counting them needs no modified crate, and what a count has to separate is a refusal at the pending hook from a handshake that failed after it. The rate they report is the floor any reaction keyed on failed handshakes has to sit above, since below it the reaction fires on honest peers. If honest failures are frequent enough to overlap what one hostile source produces, the failure count alone does not separate them and attribution or occupancy decides instead; if no honest failure is recorded in the whole window, the floor is bounded by the length of that window rather than measured, and only a longer run lowers it.

## Open questions

- **Is the Goal item about one remote's share of pending occupancy a closing condition for this issue?** It is the only item that needs occupancy attributed to a source, and what that attribution is worth depends on how far apart honest and hostile occupancy sit. **Honest reconnect peak**, read against the peak occupancy under sustained unfinished handshakes in **Per-pending-connection footprint**, shows whether the two overlap; the maintainers decide.
- **Which resource gives out first as pending inbound connections accumulate?** The Problem names memory, spawned tasks and time on the task that polls the swarm, none of the three measured, and which one gives out first decides what any bound would be set from. **Per-pending-connection footprint** covers the memory and task cost of one connection; how much of that task's time they take is {{accepts-unbounded-per-poll}}'s subject, so nothing in this issue settles that part.
- **What is the network between validators?** Link speed and round-trip times are not part of the reference deployment, and both figures under **Honest reconnect peak** depend on them: occupancy is the arrival rate times how long each connection is held, and an inbound handshake's hold time includes round trips to the peer, so neither figure is a property of the committee size alone. The maintainers supply it.
- **Does the honest failure-rate window have to close before this issue does?** The Goal's last line lists the measurements as closing conditions, and **Honest inbound handshake failure rate** cannot start until the two discarded events are counted and then needs a window long enough to contain an epoch change and a restart of a committee member. Whether the issue waits for that window, or closes on the counts and the other two measurements with the rate following separately, is the maintainers' to decide.
