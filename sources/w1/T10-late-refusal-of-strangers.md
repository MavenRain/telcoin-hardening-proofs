## Problem

The node refuses an inbound peer on three identity-keyed grounds — it is this node (`crates/network-libp2p/src/peers/behavior.rs:98`), it is banned (`:103`), or it already holds eight established connections (`crates/network-libp2p/src/consensus.rs:124`, `:136`) — and all three run only after the handshake is paid for. The 39-peer ceiling on defaults (`crates/config/src/network.rs:474`, `:489-491`) evicts after establishment instead (`behavior.rs:267-272`), validators and allowlisted peers exempt (`crates/network-libp2p/src/peers/manager.rs:894-897`).

The one earlier gate is address-keyed: `handle_pending_inbound_connection` (`behavior.rs:77-85`) is called with no peer parameter (`libp2p-swarm-0.48.0/src/lib.rs:955-959`). The swarm spawns the upgrade task (`libp2p-swarm-0.48.0/src/connection/pool.rs:478-494`), the handshake completes, and only then does `handle_established_inbound_connection` run (`lib.rs:734-739`), closing a finished connection if it denies (`:741-762`).

The identity becomes available in between, and is dropped. `certificate::parse` reads the DER first, then verifies the certificate's own signature and the one over the libp2p extension (`libp2p-tls-0.7.0/src/certificate.rs:124-132`, parse at `:127`, signatures at `:398`, `:414-417`); `verify_presented_certs` returns the resulting `PeerId` (`libp2p-tls-0.7.0/src/verifier.rs:212-225`, at `:224`), and `verify_client_cert`, the rustls entry point calling it, discards it (`:178`).

The node has no notion of a stranger — a remote whose `PeerId` is in no committee it tracks and is not on the operator's allowlist. It tracks those sets (`peer_is_important`, `manager.rs:894-897`), but they gate eviction and scoring, not admission: an unknown, unbanned identity is admitted (`behavior.rs:107`, `consensus.rs:115`).

What earlier refusal saves depends on who is refused. A `PeerId` is a hash of a freely generated key, so an attacker outside the validator set presents a new one per attempt: never this node, never banned, never over the ceiling, so refused neither early nor late. Against that attacker, earlier refusal saves nothing unless unknown identities become refusable, which no issue listed below decides. What is charged late is every refusal the node does make. A banned identity reconnecting inside the 600 s temporary-ban window (`manager.rs:267-269`; `crates/config/src/network.rs:478`) costs a full handshake per attempt, per swarm, and how often that happens is unmeasured: nothing counts a refused handshake (`crates/network-libp2p/src/metrics.rs:154-195`).

## Goal

- **A refused attempt costs the node less than it does today.** The whole server-side cost of an attempt the node refuses on identity — the handshake, and the established-inbound dispatch and denial the swarm performs on the finished connection on top of it — falls below what that same attempt costs today. That sum is the bar, so a placement that removes either part of it is measured against the same figure. The maintainers set the bound from *the handshake cost decomposition* and *what a refusal costs beyond the handshake* below, which price the two parts separately. *Observable:* those two benchmarks, and a count separating inbound handshakes by outcome, specified under *how often the node refuses anyone*. *Baseline:* the two measurements set it; today a refused attempt pays both parts in full.
- **Honest peers unaffected.** With every committee member reconnecting at once, time from first dial to established stays inside the distribution *an honest mass reconnect* below records, and none is refused while an input a refusal reads is stale, unseeded or being replaced. *Observable:* that run, reporting the distribution and refusals by reason. *Baseline:* that run sets it.
- **Non-goals.** Deciding whether an unknown identity should be refusable. The handshake-start rate ({{validated-address-handshake-rate}}). What an inbound connection attempt costs the node before any node code decides on it ({{quic-initial-unvalidated-cost}}). Repeated work inside an admitted handshake ({{redundant-cert-verification}}). What an established peer may do ({{per-peer-ceilings}}).
- The issue closes with the measurements below taken on the versions `main` resolves, the count they read in place, and a recorded choice of where in the inbound path an identity-keyed refusal runs; a record that it stays where it runs today is one such choice.

## Background

**Threat model.** The attacker is outside the validator set and is assumed to know every validator's IP address, port, `PeerId` and BLS public key. They can forge source addresses, and they can rent a botnet of hosts with real addresses. They hold no committee key and cannot break cryptography.

**Acceptance rules.** A defence has to hold when the host firewall is absent or wrong, and has to fail open when an input it depends on (a committee list, an address list) is stale or missing, so honest peers keep connecting. Floods that saturate the link are the hosting provider's to absorb and are out of scope; the scope is what such an attacker can do to the node's CPU, memory and tasks at packet rates the NIC still delivers.

**Node shape.** Each libp2p swarm has one public QUIC listener on one UDP socket. A node runs one swarm for the primary and one per worker (`crates/node/src/manager/node.rs:1244`, `:1282`), all built by `ConsensusNetwork::new` (`crates/network-libp2p/src/consensus.rs:406`), so every per-swarm limit or cost multiplies by the number of swarms on the host.

Paths under `crates/` refer to `main` at `9b2a06b7`; a path that begins with a crate name and version, such as `libp2p-quic-0.14.0/src/transport.rs:595`, refers to the crates.io source of the version `Cargo.lock` resolves.

**Reference deployment.** The maintainers' reference deployment is a committee of ten validators, each on an Ubuntu server with 8 CPUs and 32 GB of RAM, running one node process with two swarms (the primary's and one worker's). The network between validators (link speed and round-trip times) has not been specified.

The listener itself does no address validation in the sense of RFC 9000 section 8.1, accepting every incoming attempt unconditionally (`libp2p-quic-0.14.0/src/transport.rs:595`), so a remote forging its source address never presents a certificate at all.

TLS 1.3 fixes what an earlier refusal can reach. The server authenticates the client last: its key exchange (`rustls-0.23.37/src/server/tls13.rs:502`, call site `:342`), its `CertificateVerify` signature (`:787`, call site `:394`) and its `Finished` — its first flight — precede its read of the client's certificate (`:381`, `:441-447`). Resumption is live server-side on rustls' defaults (`libp2p-tls-0.7.0/src/lib.rs:71-93`; `rustls-0.23.37/src/server/builder.rs:110`, `:120`), and a resumed handshake — from a stored ticket, not a certificate exchange — requests no client certificate (`tls13.rs:340`, `:380-381`); the server enables no early data (`builder.rs:118`), so resumption shortens the handshake without letting the peer send ahead of it.

### Approaches surveyed so far

Each is a placement: a point in the inbound path at which an identity-keyed refusal could run. All three sit in dependency crates, so each arrives as a modified crate — the upkeep {{patched-transport-crate-upkeep}} describes — or upstream.

Client-certificate verifier, which derives the identity from the DER before either signature verification (`libp2p-tls-0.7.0/src/verifier.rs:212-225`). Constraint: `libp2p-quic` keeps both rustls configurations private and builds them itself (`libp2p-quic-0.14.0/src/config.rs:65-68`, `:81-85`), a resumed handshake does not reach it, and rustls returns the refusal as a TLS alert, not a libp2p denial.

Pending-inbound hook, the only gate before a handshake starts. Constraint: it is handed a connection id and two addresses, no peer parameter (`libp2p-swarm-0.48.0/src/lib.rs:955-959`), and it returns before the swarm spawns the upgrade task that runs the handshake (`lib.rs:985`; `libp2p-swarm-0.48.0/src/connection/pool.rs:478-494`), so no certificate has been exchanged when it runs and an identity would have to reach it through the behaviour trait and the transport beneath.

Transport upgrade step, where `libp2p-quic` parses the peer's certificate again for the `PeerId` it hands the swarm (`libp2p-quic-0.14.0/src/connection/connecting.rs:75-77`). Constraint: it runs after the handshake has completed (`:84-92`), so what it precedes is the established-inbound dispatch and denial the Problem describes, not the handshake, and it reports failure as a QUIC transport error (`connecting.rs:56-63`), not a libp2p denial.

## Implementation details to pay close attention to

If a refusal is evaluated before the certificate's signatures have been verified (`certificate.rs:398`, `:414-417`), the identity it acts on is unproven: the check can refuse a peer that never connected and admit one that did.

If an earlier check is the only gate, a resumed handshake and a stale set both bypass it: a peer whose status changed returns on a ticket without it running (`rustls-0.23.37/src/server/tls13.rs:333-338`).

If a check fails closed while the set it reads is stale, unseeded or being replaced, honest peers are refused when that set is least reliable: a restart before the current committee has been written into the node's peer records, which happens once per epoch from authoritative state (`crates/network-libp2p/src/peers/manager.rs:899-914`), an epoch boundary, a partition heal. Failing open leaves the refusal absent in those windows.

If a refusal changes what the dialer observes — a TLS alert, a transport-level error, a connection closed before the handshake rather than after it, or a different certificate or handshake shape — stock dialers of this and the previous release classify it differently, and the outcome count the Goal above asks for is what would make that visible on the server.

## Measurements that would affect the decision

**The handshake cost decomposition**, re-taken on the versions `main` resolves. It measures where a full inbound handshake's server CPU falls either side of the moment the peer's certificate can be read. Refusing an inbound peer inside the client-certificate verifier, before any signature verification runs, cost the server 92.0 µs of CPU at the median, against 285.8 µs for the full handshake, in an in-process benchmark on one desktop-class Intel CPU with `libp2p-tls` 0.6.2 and `rustls` 0.23.37 on the ring provider; those 92.0 µs are what a refusal at that point has already paid, being the server's own key exchange, signature and first flight, which TLS 1.3 spends before it ever sees the peer's certificate, and this is not reproduced on current versions. That pair is the one existing measurement of any placement surveyed above; the other two have never been measured, and what follows the handshake is priced by *what a refusal costs beyond the handshake* below. The re-take reports the split in the handshake, not a placement's saving. Rebuilding it: an in-process driver over the real `libp2p_tls` configurations, server CPU summed per connection on one pinned core of a reference host (see Background), for an establishing attempt and a refused one. Decision rule: a small share of CPU falling after the certificate means placement buys little; a large share means placement decides the saving; if the two figures fall within measurement noise of each other, no placement earns its cost.

That provider has since changed, unevenly: `libp2p-tls` 0.7.0 builds both rustls configurations on `aws_lc_rs` (`libp2p-tls-0.7.0/src/lib.rs:48`, `:76`), which bears on the work before the certificate, while the parse's own verifications run on `ring` and, through `libp2p-identity`, on `ed25519-dalek` (`certificate.rs:305-325`) — resolved at 3.0.0, also not measured. Inside that parse, reading a `PeerId` out of a peer certificate without verifying any signature works out to roughly 5 µs: the 70.6 µs full parse less the two signature verifications it contains. That is arithmetic on separately measured microbenchmark figures taken on one desktop-class Intel CPU with `libp2p-tls` 0.6.2, not a direct measurement, and it is not reproduced on current versions. Those two figures separate the cost of reading an identity from the cost of proving it, which is the split the first hazard above turns on.

**What a refusal costs beyond the handshake**, which nothing measures today. A refused attempt is charged for more than its handshake: the swarm dispatches the finished connection to the behaviour (`libp2p-swarm-0.48.0/src/lib.rs:734-739`), and on a denial it builds the error, hands it to every behaviour as a listen failure and queues it as a swarm event before that finished connection is closed (`:741-762`). What to measure: an in-process driver that gives a swarm inbound connections its behaviour refuses, and inbound connections it admits, with server CPU summed per connection on one pinned core of a reference host (see Background), taken at the node's own boundary so that no dependency crate has to be modified to read it; the handshake figures above then separate what the refusal itself adds. What it has to tell apart is what the count under *how often the node refuses anyone* tells apart: an attempt that finished its handshake and was admitted, and one that finished its handshake and was refused. Decision rule: if what the refusal adds is small beside the handshake that attempt has already paid, the first Goal item's bound is set by the decomposition above alone; if the two are comparable, that bound has two terms and a placement is measured against whichever term it reaches; if the refused and admitted runs cannot be separated from measurement noise, the whole server-side cost of a refused attempt is its handshake.

**How often the node refuses anyone.** The count this reads separates inbound handshakes that finished and were admitted from those that finished and were refused, and splits the refusals by reason: this node, banned, over the per-peer ceiling. Its admitted half exists in node-owned code already, as the established-connection metric with its `in` direction (`crates/network-libp2p/src/metrics.rs:154-160`, recorded at `crates/network-libp2p/src/peers/behavior.rs:253`); its refused half is the one the Problem says nothing keeps, and of the three reasons two are decided in the node's own behaviour and the third by the connection-limits behaviour it installs (`consensus.rs:205`). With that count, read refusals by reason from a committee node over an epoch, from both swarms of the one node process the reference deployment runs. Decision rule: if banned identities rarely return inside the 600 s window, late refusal costs almost nothing today and the saving waits on whether unknown identities become refusable; if they return steadily, the decomposition sizes it; none at all leaves only the policy question.

**An honest mass reconnect** on the reference deployment (see Background): ten validators, each running one node process with two swarms on a reference host. That is nine remote committee members per swarm and two swarms per host, so each host sees eighteen committee handshakes in the burst (derived from the reference deployment, not measured), alongside any non-committee peers reconnecting in the same window. Report time from first dial to established, which the network between validators sets and the reference deployment does not specify, and the share of reconnects that resume rather than handshake fully. What separates the two on the server is the client-certificate request described in Background, and node-owned code cannot see it: the transport hands the swarm an established connection and a `PeerId` either way (`libp2p-quic-0.14.0/src/connection/connecting.rs:90-92`; on a resumed handshake the client certificate chain stored with the ticket is restored, `rustls-0.23.37/src/server/tls13.rs:333-338`), and the server configuration that knows is the one `libp2p-quic` builds and keeps private (`libp2p-quic-0.14.0/src/config.rs:65-68`, `:81-85`), so reading the split on a node would depend on the modified-crate upkeep {{patched-transport-crate-upkeep}} describes. Reading the code does not settle the dialer side either. `libp2p-tls` builds the client configuration without touching resumption, so rustls' default store applies (`libp2p-tls-0.7.0/src/lib.rs:42-68`; `rustls-0.23.37/src/client/builder.rs:168`); that store is keyed by server name (`rustls-0.23.37/src/client/handy.rs:73-75`, inserted at `:155-168`, taken back at `:171-179`), and `libp2p-quic` dials every peer under the single name `"l"` (`libp2p-quic-0.14.0/src/transport.rs:302-306`), so one node's tickets for all of its peers share one entry and a dial takes the most recently stored. What a resumed handshake costs the server has been measured: 86.0 µs of CPU at the median for the PSK binder and key schedule, no certificate flight, in an in-process benchmark on one desktop-class Intel CPU with `libp2p-tls` 0.6.2 and `rustls` 0.23.37 on the ring provider; only a returning peer that already holds a session ticket can reach that path, and it is not reproduced on current versions. Decision rule: a high resumed share means a check that only a full handshake reaches is skipped for most honest reconnects, and that most honest reconnects cost the server the 86.0 µs above rather than the 285.8 µs of a full handshake; a low share means it sees nearly every one, at the full price. This run is also the regression guard's baseline.

## Open questions

- **Should an identity the node has never seen be refusable at all?** The node admits unknown, unbanned identities today, so the only refusals a placement can move earlier are the three the node already makes. The answer changes what the first Goal item is worth, and what the count *how often the node refuses anyone* reports implies. It is a policy decision for the maintainers, and no issue listed below makes it.
- **Should a placement be chosen before, alongside, or after that policy decision?** A placement chosen now is chosen against the three identity-keyed grounds the node has today; a policy on unknown identities would change that set, and with it what a placement has to reach and how often it runs. This issue closes on a placement recorded, so the order in which the two are settled decides what that record answers. A decision for the maintainers; the policy itself would belong to a separate issue.
- **Does a returning peer ever resume, and how often?** Reading the code does not settle it, for the reason given under *an honest mass reconnect*: one ticket store shared across every peer a node dials. The resumed share decides whether the resumption bypass among the hazards above is reachable at all; *an honest mass reconnect* reports that share once the split it rests on can be read on a node, and says there what reading it would take.
- **What network sits between validators?** The reference deployment does not specify link speed or round-trip times, and they set the dial-to-established distribution *an honest mass reconnect* reports, which is what the second Goal item is measured against. An input the maintainers supply.
